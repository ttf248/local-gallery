本文维护当前模块入口、数据流与修改时必须守住的边界。接口字段见 [API.md](./API.md)，产品结构与产品问题见 [PRODUCT.md](./PRODUCT.md)，界面规则见 [DESIGN.md](./DESIGN.md)，运行与验证命令见根 [README.md](../README.md)。

## 模块与依赖

系统是单 Go 进程、本地媒体文件、JSON 状态与浏览器 UI。开发由 Vite 代理 API，生产由 Fiber 单端口提供 API 和前端静态文件。

```text
React routes/components → api + TanStack Query（服务端状态）
                       → Zustand（客户端状态）
        │ 资源 ID / JSON / SSE
        ▼
Fiber middleware → handlers → services/store → models + 本地文件
```

## 资源快照与安全边界

`ResourceCatalog` 是绝对路径转换为公共 ID 的唯一组件。`r_`、`a_`、`c_`、`f_` 分别代表根、相册、集合和文件；由根标识、资源类型与相对路径派生，路径不变时稳定，不可逆推出完整路径。

发布时构建 raw 扫描结果、ID 表、manifest、目录直属子项、全局相册、媒体自然顺序、标签与搜索索引，集合统计聚合全部后代。结果与索引通过一次原子指针更新发布为同一 revision，分页请求不重新遍历目录树。

每个请求只 Acquire 一次 `CatalogSnapshot`，资源参数中间件把快照固定到 Fiber Locals，handler 沿用同一版本。分页游标绑定 revision 和作用域，重扫后的过期游标由客户端丢弃已合并页面后重新读取，具体错误见 API。作用域是全等比较的字符串，列表作用域带内容属性段（`library-children:<父 id>:<属性>`、`library-unread:<属性>` 等），跨属性复用旧游标会被拒绝为 `invalid_cursor`。

请求先过 `AccessGate`，再解析资源与校验路径。门禁检查 Host、Origin / Fetch Metadata、local/LAN 认证；配置与目录管理再加回环限制。LAN SSE 使用 HttpOnly 同源会话，不把令牌放 URL；会话驻留内存，令牌轮换使旧会话失效。当前服务不终止 TLS，使用边界是本机或可信家庭网络。

ID 只能证明扫描时的身份。每次媒体、批量元数据及系统打开请求仍通过共用 `PathValidator` 按当前根校验：

- 用最具体的配置根授权，与根顺序无关；显式链接根允许作为边界，根内未单独配置的符号链接/junction 拒绝，失败不回退到更宽的父根。
- 逐级检查扫描后替换的链接，文件资源须仍是普通文件，目录资源须仍是目录；失效先于 ETag、Range、派生缓存及发送，不产生暴露路径的目录重定向。
- 绝对路径只保留在后端及受回环限制的配置管理交互中；日志、公共错误与媒体响应只给别名、相对路径或稳定 ID。

这不提供针对受信本机进程任意并发改写文件系统的事务隔离。配置文件含本机路径与令牌，Unix 加载/写入收紧为 `0600`，Windows 使用仅授权当前用户的受保护 DACL，失败则拒绝加载或保存。

## 扫描与库发布

1. `NormalizeRoots` 相对 CWD 绝对化、去空并保序去重；Windows 忽略大小写，其他平台区分大小写。规范化不读取目录、不解析链接，离线根仍可用于配置和缓存等价比较。
2. `StartOrReuse` 全局复用一个活动扫描，记录根身份与可读性；每个根读取前后、整理后及提交前复核，空根合法。根消失、不可读、被替换则整轮失败，保留已发布快照与磁盘缓存。
3. Scanner 使用 `min(8, NumCPU)` 个固定目录 worker，协调器派发子目录、worker 返回记录，枚举后建树，不递归占用令牌等待子任务。每个根的子 context 在成功、失败或取消时关闭并等待全部 worker。
4. 父根遇到单独配置的子根时委派给子根，归属取最具体根，不重复统计或增加包装集合；未配置的链接跳过并告警。普通子目录读取失败仅在根仍有效时降为脱敏告警。
5. 目录含普通文件 `.nomedia` 时，扫描器跳过该目录的媒体及所有子目录；根目录也遵循此标记。删除标记并重新扫描后，目录会重新进入图库。
6. 构造候选结果并叠加仍有效的自定义封面，验证 scan generation，然后一次发布结果与资源/分页索引；持久化扫描缓存，最后发送带 revision 的 complete。

混合目录生成集合和“本目录媒体”虚拟相册，两者共享真实目录但 kind/ID 不同。虚拟相册的 `name` 是固定类型标记，展示和搜索使用 `location` 相对路径；同名目录不能只靠 basename 区分。目录与媒体自然排序。业务日期由扫描层按 `filename > folder > modified` 解析：`filename` 是从文件名推断的拍摄时间（相机与手机普遍把时间写进文件名），不读 EXIF，因此不引入随机 I/O；前端时间线不重复猜目录日期，“最近改”另外使用 `modTime`。集合也带时间：目录修改时间与后代相册拍摄时间的代表值（按媒体数加权取众数）。

媒体根规范路径或内容属性变化时，配置 handler 串行执行保存、推进 generation、取消旧任务、清库并启动最新根扫描；空根仅清库。旧任务保留登记至回收，但不再被新扫描复用，退出等待新旧任务全部结束。等价根写法和重排不清库或重扫。自定义封面在发布前统一叠加到各引用视图，不能让卡片、详情与标签封面分裂。

### 扫描缓存与 SSE

- `ScanResultCache` 只负责重启恢复与落盘，磁盘含 raw 路径，不作为 HTTP 数据源；schema 版本取 `scanCacheSchemaVersion`，不匹配时隔离并冷启动。恢复比较规范化根 ID 集合，拒绝重复根及实体树中同 kind 的重复路径，允许虚拟相册和集合共享目录、标签重复引用相册。
- 缓存读取用原子指针，更新用 Store/CAS；文件检查移出锁，500ms 防抖落盘，版本号确保 flush 期间的新写入不被误标为已保存。清空与落盘互斥，退出强制 flush。
- SSE 每连接显式订阅并持有释放函数，独立缓冲避免慢客户端阻塞扫描；连接关闭释放订阅与心跳，不取消共享任务。每 15 秒注释心跳，终态或通道关闭结束连接。
- 订阅注册与最新快照取得保持一致，重连恢复原阶段、耗时、数量、进度与 revision。任务终态短期保留后回收，不能重新启动扫描来恢复进度。
- 进度按根与阶段估算且不回退，根读取累计 0–95%、整理 99%，成功发布才为 100%；取消/失败保留最后有效进度与脱敏路径，不发布部分结果。

### 自动发现文件变化

目录监听、增量扫描与分析任务串成一条链路，全部在后台运行，复用既有的扫描任务与分析任务中心，不新增第二套任务体系。

- **监听**：`ChangeWatcher` 基于 fsnotify（Windows 上走 `ReadDirectoryChangesW`）监听已配置的媒体根。只登记扫描器会读取的目录：被排除规则跳过的目录、符号链接、独立配置的子根与带 `.nomedia` 标记的目录都不监听。新建目录自动登记，删除目录自动摘掉。Windows 的目录监听不是递归的，因此每个目录各占一个句柄与一块事件缓冲区（8 KiB）；监听目录数量有上限（1 万），超出部分与事件溢出由定期校验兜底，内存与句柄因此有界。单个媒体根读不到（离线磁盘、断开的网络共享）不算监听降级，其余根照常工作。
- **去抖与合并**：连续事件在静默窗口（2 秒）内合并成一批，批量复制因此只产生一次同步；单批最长等待 30 秒，避免持续写入永远等不到静默。文件仍在写入时推迟提交：连续两次观测之间大小没有变化才算写完，因此写了一半的图片不会进索引。批次在提交前先从待处理集合里换走，换走之后这一批只归提交逻辑所有：事件处理往新批次里写，两边不碰同一份数据 —— 高频写入时否则会撞上「并发读写同一张表」而整个进程退出。提交期间到达的新事件不会被搁浅：提交收尾时若还有新变化在等着，就重新排一次提交 —— 提交线程已经醒过一次，不会再有第二次唤醒，把计时器抹掉等于让这批变化一直等到下一次文件变化才有机会提交。文件一直写不完时按当前状态强行提交，但提交过的那一批不再留在待处理集合里，避免同一批变化被交两次。
- **增量扫描**：`IncrementalEngine` 复用上一份扫描结果，把上一份结果展开成按目录索引的树。内容变了的目录重新读取，未变化的子树整段复用；目录结构变了（叶子相册变成集合、或反过来）时重建该目录的祖先。合并结果是一份完整快照，由资源索引原子发布，中途失败保留上一份可用图库。增量发布与全量扫描共用扫描任务的提交锁，并校验图库版本：期间有别的发布就基于新图库重算，两份结果不会互相覆盖。
- **结构变化与内容变化**：每本相册带一个内容指纹（媒体文件的大小与纳秒修改时间汇总出的哈希）。文件清单变了是结构变化；清单没变而指纹变了是内容变化 —— 原地覆盖一张照片属于后者。只比路径与目录修改时间认不出后者，认不出就等于「照片被覆盖了但图库不知道」。增量结果分别报出两种变化：结构变化决定资源索引要不要重建，内容变化决定哪些分析结果要作废。集合目录（下面还有子目录的那种）原先散落的照片被删掉时同样要报成删除 —— 不报的话那些照片的分析结果会留在任务中心里，对着已经不存在的文件。
- **离线的根**：某个媒体根读不到时，增量更新保留它上一份的内容，其余根照常更新 —— 一个断开的网络共享不该让本地目录的变化也一起丢掉。待处理的变化集合有上限，攒到上限就丢掉旧的并改用一次全量校验兜底。
- **发布判定**：图库结构与相册内容都没变时（例如只是目录被碰了一下）不发布，图库版本不跳动，界面也不用白刷一遍，也就省掉一次整库资源索引的重建。
- **失败与重试**：增量扫描失败时这批变化不会丢 —— 它们放回待处理集合，等下一轮再试（不立刻重试，避免磁盘一直读不了时忙等）。连续失败超过 5 次才放弃这批，并改用一次全量校验把图库对齐。
- **分析联动**：增量更新后按差异为变动的照片排分析任务。任务限定在变动的资源上，并由任务自身按文件指纹（大小与纳秒修改时间）判断该不该重算，因此没变过的照片不会被重复分析，被覆盖过的照片一定会重算。排队是分批的：一批最多 500 张，任务中心同一时刻只跑一个任务，下一批等上一批结束再排 —— 一次导入几千张也不会把任务中心一次塞满。队列超出上限（5000）时不丢任务，而是改成让该模块做一次全库增量分析，由任务中心按文件指纹挑出真正要重算的那些。排队失败（模型没装好、磁盘读不了）时任务留在队列里重试，超过 3 次才放弃并记下原因；全库增量分析的标记同样如此 —— 提交失败时标记留着等下一轮，不会因为一次失败就丢掉这批工作。提交出去的标记要等任务真的跑完才清：任务中途失败时那批资源放回队列重试，全库分析则重新提交一次 —— 提交成功就清标记的话，任务失败就再也没人接手，那批照片的分析结果永远补不上。欠着的活按代次记：全库增量分析的任务带着启动时的代次回来，代次没变才销掉这一笔 —— 任务在跑的时候又导入超过上限的一批照片，那是一笔新的欠账，旧任务跑完不能把它一起清掉。任务记录从任务中心消失（用户清了历史）时当作失败处理：这批资源放回队列重试，全库分析的欠账留着重新提交 —— 记录没了不等于活干完了。放弃一批失败的工作时只放弃这一批，后来排进来的资源不受影响。离开图库的资源，其分析结果一并作废。自动分析可以在设置里暂停；暂停后图库照常更新，只是不排分析任务。
- **智能相册重算**：分析结果更新之后要重算智能相册，等所有模块的活都干完、任务中心空闲下来才触发一次增量刷新。队列被清空换成全库分析时同样算「有活要干」—— 只看队列长度会漏掉这一种，派生结果会停在导入之前。要重算的标记只在刷新真的跑完之后才清：刷新启动失败或中途出错时标记留着并自动重试（失败后隔 30 秒再试，避免一直失败时刷出一串失败记录）；刷新期间又有新照片进来时这次结果不算数，标记继续留着。复用的那次刷新（用户手动点的、每日计划跑的）开始得更早，覆盖不到后来的变化，它跑完不能算覆盖了当前这一代 —— 标记要留着，下一轮自己再开一次。派生数据停在旧状态而界面上看不出哪里不对，只能等用户手动点一次 —— 那不是能接受的兜底。
- **重启接续**：欠着的分析记在 `state/library_sync.json` 里（哪些模块欠活、要不要重算智能相册）。进程被杀时内存里的队列会没，但磁盘上还留着这份记录：重启后把它变成一次全库增量分析，任务中心按文件指纹挑出真正要重算的那些，欠的活一定在内 —— 派生索引最终要与实际媒体库一致。
- **兜底**：程序关闭期间磁盘上的变化不会产生事件，启动后 15 秒做一次校验扫描补上；此后每 30 分钟校验一次，监听报错时也立刻校验，重新打开监听后也会补一次。校验走既有的扫描任务，进度、取消与 SSE 全部复用。校验到点时若正好有扫描在跑（用户手动扫的、上一次校验还没结束），只能复用那一次 —— 而那次扫描可能早于校验就开始了，覆盖不到校验这段时间的变化，因此不能拿它当校验结果：等它跑完再补一次真正的校验。校验发现的差异要排进分析：程序关闭期间的变化不会有事件，增量扫描那条路发现不了，不排的话新照片永远没有分析结果，派生索引与媒体库永远对不上。相册的内容指纹是整本聚合出来的，说不清是哪一张被改写时改成一次全库增量分析，由任务中心按文件指纹自己挑。

### 四层数据的边界与统一规则

四类数据各有各的存法，规则统一如下：

| 层 | 位置 | 可否重建 | 读不出来时 |
| --- | --- | --- | --- |
| 用户原始媒体 | 媒体根 | 不可重建 | 目录失效，不进图库 |
| 只读资源索引 | 内存快照 | 可重建（重扫） | 沿用上一份快照 |
| AI 分析结果与向量索引 | `derived/` | 可重建（重跑） | 按缺失处理 |
| 用户确认、命名与排除关系 | `state/` | **不可重建** | 报错并保留原文件，不静默清空 |
| 任务状态、检查点与调度设置 | `state/ai_jobs.json` | 不可重建 | 报错并保留原文件 |

三条统一规则：

- **版本失效只有一份判据。** 「既有结果对这张文件是否仍然有效」由 `aiRecordIsCurrent` 回答；任务开跑与空闲时的规模预估都走它，因此预估出来的张数与任务实际的 `planned` 对得上。人物索引与智能相册缓存各自按同一口径（大小 + 纳秒修改时间 + 模块版本）比对。
- **落盘顺序：先用户状态，后派生数据。** 派生索引可以重算，用户纠错不能。让可重建文件的写入失败挡住不可重建文件的保存，等于用一次磁盘错误换掉用户改过的东西。人物服务、人物索引发布与智能相册改名迁移都按这个顺序。
- **改名迁移分两步。** 智能相册的分组换号时，先写下新键，等派生缓存落盘之后再删旧键。顺序反过来的话，进程在两次写之间退出时旧键已被删掉、缓存里却还是旧分组，用户改过的名字就没有出处了。

规模核算的降幅来自一处具体改动：文件指纹清单原先按模块分组缓存，一次核算要把全库 stat 六遍；现在按口径（全部图片 / 仅照片侧）分组，四五个模块共用同一份清单。

人物增量的降幅来自另一处：增量快路径原先每次都克隆四张全量映射表与一份人工纠错，一个都用不到；差额随人脸数增长，一万张脸时每次增量少分配约 3.7 MB。

人物索引的降幅来自两处。一处是 ANN 索引本身：点积是这张索引里最热的一处（CPU 采样里占 94.6%），单个累加器时每一步都要等上一次加法结束；改成四个互不依赖的累加器，再把搜索的暂存区复用起来，建索引快一倍、分配少七倍。另一处是更新的粒度：原先每批结果进来都要把整库重新聚类一次，一万两千个分组上就是 67.6 秒 —— 整库分析要重算几百遍。现在每批只做增量，任务收尾时整体重建一次。

真实库（13,478 张照片、24,148 张脸、12,329 个分组）上量到的三笔账：启动时按缓存还原分组 4.8 秒；一个任务里第一批要建 ANN 索引，29.7 秒（每个任务一次）；之后的每批 0.23 秒；任务收尾的整体重建 42.6 秒，在后台跑。整库分析因此从「每批重算一遍」变成「开头一次、结尾一次，中间每批零点几秒」。

人物列表的降幅来自第三处：列表每次请求都要算照片统计、排出前五十个分组，这两条路径原先都把全量人脸整张复制一遍（连特征向量也带着走），再给每个分组各建一张「分组 → 照片 → 人脸」的嵌套表。现在照片统计只留一条轻量记录（资源、分组、框、检测分），去重改用「(分组, 照片)」组成键，按资源与按分组各汇总一次。

照片统计有两种口径。合影判定分三档：脸数超过门槛（20 张）就是合影，脸数不足八张就不是合影，只有中间那一档要看人脸相对尺寸。而查原图尺寸要落盘：先过路径安全校验（逐级 Lstat），再 stat 一次文件。所以只要分类的调用方（人物列表、匹配建议、标注抽样）用只算分类的口径，不必查其余资源的尺寸；合照候选页要显示人脸相对尺寸的分位数，就只给挑出来的候选分组查尺寸。

真实库（13,478 张照片、24,148 张脸、6,066 张有脸的照片）上量到的差别：人物列表一次请求原先要 1.2～1.9 秒，几乎全花在查原图尺寸上；改成只算分类后，六千零六十六张有脸的照片只剩 758 张要查（脸数在八到二十张之间那一档），请求降到 0.24 秒。合照候选页从 1.4 秒降到 0.38 秒。两种口径的分类结果逐项相同，`TestPeopleGroupPhotoClassificationsMatchFullStats` 锁住这一点。

待确认匹配页第一次打开要 45 秒：人物 ANN 索引要在内存里重建（约 33 秒），再为全部分组各做一次近邻查找（约 12 秒）。这是既有成本，本次重构没有改动它 —— 只是 ANN 索引本身快了一倍。

### 持锁范围

三处服务都把「读内存」与「做磁盘操作」分开，磁盘操作不占着状态锁：

- 任务状态锁下不做磁盘操作。清除模块结果时删目录、忘掉资源时改写批次文件、读取拍摄时间时解析 JSON、复制分析结果载荷，全部在锁外做。
- 智能相册的构建锁按「相册 + 维度」分锁，不是全局一把。给场景分组取名字要等本机的文本嵌入 Worker，最长二十秒；一把全局锁意味着一本相册在等 Worker 时别人的相册也只能干等。同一把锁仍然只算一遍，不同相册可以同时构建。
- 用户的改名与隐藏是短状态，写在 `state/`；分组成员是可重建的派生数据，写在 `derived/`。两者不共用一把锁。

quality-v2 的人脸 Worker 在 CPU 与 GPU 路径统一使用 YuNet 0.75 最低检测分；提交 SFace 前还会要求分析图上的人脸框最短边至少 32 像素，并检查框尺寸、有限坐标与五点关键点的基本几何关系。Buffalo_m 保留 640 像素全图快检；当检测到至少 8 张脸、检测图长边达到 2048 且至少检测到 4 张脸，或有人脸框长边不超过图像长边的 4% 时，顺序补跑 1280 像素图块，再将图块坐标还原并做全图 NMS。普通照片最多提交 64 张脸，触发图块检测的照片最多提交 256 张；GPU 图片并发从普通照片的 4 降到图块照片的 2，超过 350 万像素时降到 1。分析图最大长边为 2048，图块推理不会同时保留多张高分辨率副本。人物索引重建会对旧批次按相同分数门槛过滤，并通过当前安全校验后的源图尺寸还原到 2048 像素分析尺度，要求脸框最短边至少 32 像素；尺寸未知时保留旧框尺寸门槛。旧记录没有关键点，不能补做关键点几何检查，因此完整质量门仍需重跑人脸任务。旧版本结果在文件指纹仍匹配时继续可查看，新的分析版本会让任务估算识别待重算项。人物分组版本更新会重建可派生索引，同时按成员重叠迁移用户的改名、隐藏与手动分组修正。

人物自动聚类按当前模型独立使用中心、锚脸、组间复核等阈值；quality-v2 与 Buffalo_m 启动时沿用现有阈值，但策略配置彼此隔离。候选脸须与在线中心余弦高于 `0.520`，且与创建该组的固定锚脸高于 `0.720`。锚脸不随置信度更高的新脸替换，防止一串相邻但不同身份的匹配逐步拖动中心并链式合并。初步分组后再检查组间是否有高置信度重复：只检查组中心 HNSW 的前 64 个候选，每个来源组按资源 ID 均匀抽样最多 256 张脸；组中心相似度至少 `0.820`，两组各有至少 10 张脸，且没有共同来源照片；跨组至少有 `max(2, 较小组脸数的 5%)` 组互为最近邻的人脸对，每对相似度至少 `0.720`、平均相似度至少 `0.750`。多组归并要求组件内任意两组都有直接匹配证据；合并来源 ID 会写入可重建索引，增量更新时也逐一检查已合并组的每个来源组，避免后续批次借聚合中心形成链式扩张。有改名、隐藏或人工分配的人物组不参与自动归并。该复核可以找回跨年龄或画质变化而分裂的同一人，同时保留用户手动纠错入口；自动组仍是候选身份，不是身份确认。分组策略变化会递增 `peopleGroupingVersion`，强制从当前有效脸记录重建索引。

人物分组质量回归使用确定性的合成向量样本，覆盖近邻同身份与逐步漂移的异身份边界；测试按脸对输出 precision、recall、F1 和 TP/FP/FN/TN，不在仓库保存真实照片或真实人脸特征。真实指标由 `backend/aiworker/evaluate_people.py` 驱动当前 Worker 检测并生成人脸向量，再把临时记录交给 `cmd/people-eval` 的生产人物分组实现；身份标签、照片路径与向量只留在本机临时目录，JSON 报告不含这些原始值。

待确认匹配和自动聚类分开：少于 3 张照片、未确认且不只出现在合照中的组作为人工复核源；目标必须已由用户确认，或至少包含 10 张脸且出现于 3 张照片。系统只提供最多 3 个按多脸相似度排序的对象，不自动变更组关系。跨照片互为最近邻证据要求至少两组不同照片；证据不足时可按更高单组门槛提示，但 UI 标记为模糊建议。用户可显式合并、排除一对组或固定保留源组；人工状态分别保存稳定人脸键和组 ID，并按当前模型隔离。每张照片结果上限为 256 张脸，与脸部序号、状态备份和当前索引限制同步。

### 相似照片与连拍整理

这一功能复用既有的后台任务系统、语义向量索引与照片级精选，不引入新依赖、新服务或新数据库。特征提取是新增的分析模块 `similarity`，纯 Go 实现：读文件字节算 SHA-256 内容指纹，按 EXIF 方向归一化后解码，算 64 位 DCT 感知哈希（pHash）、64 位横向差分哈希（dHash）与三档中心裁切哈希，再按长边折算到 1024 的灰度副本算清晰度（3×3 拉普拉斯响应的方差）、百万像素、曝光均值与高光/暗部占比。质量分项按清晰度 0.45、分辨率 0.25、曝光 0.30 加权得到代表评分，与文件大小无关。HEIC/HEIF 复用既有的 ffmpeg 格式转换后再解码；该模块固定用 CPU，不占用 GPU 推理。

三类结果各自独立计算：

- **完全重复**按 SHA-256 分组，可以跨文件夹 —— 同一张照片存到两个地方是最常见的重复来源。
- **近似重复**只在文件夹内比较。先用分带索引召回候选：64 位哈希分成 8 段各 8 位，汉明距离不超过 7 的两个哈希至少有一段完全相同（鸽笼原理），因此 8 段索引必定召回候选；候选再逐一复核整幅哈希、中心裁切档位哈希与长宽比。语义向量可用时它是一道否决线（余弦低于 0.72 即判为不同画面）；向量缺失时裁切阈值从 8 收紧到 6，宁可少召回也不误报。
- **连拍同场景**按 EXIF 拍摄时间窗口（90 秒）加相似度判定：语义余弦不低于 0.92，或感知哈希距离不超过 8，或两者联合达标。没有拍摄时间时退回文件修改时间，并因此收紧门槛。连拍组里的照片画面不同，不按重复处理。

召回分阶段进行，避免全库两两比较；单个文件夹的候选对数量有上限，触到上限时分组结果标记 `limited`，界面如实说明结果可能不完整。

分组结果是可重建的派生数据，写在 `derived/ai/similarity/groups.json`；人工决定（已审查、忽略、指定代表照片）写在 `state/similarity.json`。组的标识取组内最小的资源标识，组变大变小都不换号，因此重建后用户的决定仍然对得上。

锚点那张照片被删掉时标识会跟着变 —— 决定必须跟着照片走，不能跟着标识走。重建时按三样把旧组与新组对上：**分组类别**（完全重复与近似重复是两回事，不互相迁移）、**成员重叠**（两组有共同的成员）与**旧组锚点**（拆组时含有锚点的那一组才是原来的那一组）。对上之后把决定迁到新组的标识上，并清掉旧键 —— 留着的话别的组可能撞上同一个标识，把这份决定套用过去。合组（多个旧组合成一个）以锚点所在的那一组为准，它的标识本来就是新组的标识；其余旧组的决定归属说不清，保留在原处但不套用。合出来的组比旧组都大（没有旧组的标识与它一致）时，多份决定只要有一处对不上 —— 包括两组各指定了不同的代表照片 —— 就不套用。归属实在说不清时（拆组且锚点已经不在、重叠又一样多）原始决定原地不动：宁可让用户再看一遍，也不要把决定套到错的组上。代表照片只在还是组内成员时才继续算数，否则退回推荐的代表。分组在分析结果提交后由后台静默期重建，不阻塞分析任务。批量加入精选复用既有的照片级精选集合，不新增第二份数据源。

### 人物评测

一次历史本机对照使用 RTX 3060 与 51 张照片、81 张脸、42 个匿名身份：quality-v2 检测 precision/recall 为 0.872/0.926、身份 pairwise 为 0.778/0.656；Buffalo_m 全图分别为 0.915/0.926、0.820/0.641；Buffalo_m 自适应分块分别为 1.000/1.000、0.827/0.672。匹配建议旧口径展示 0/11 对，新口径展示 2/11（召回 0.182、准确率 1.000）。该标注集未纳入仓库，当前 checkout 无法复现这些数值；它们只记录历史实验，不是可保证的质量基线或阈值依据。当前准确率、小脸召回、Buffalo_m 分块收益与 GPU 显存峰值仍待可复现样本和设备侧工具验证。

本机标注集使用 JSON `schemaVersion: 1`，每张照片需要一个仅本机使用的 `resourceId`、相对于清单的图片 `path` 和人脸标注。框坐标采用 EXIF 方向校正后画面里的源图像素 `[x, y, 宽, 高]`；`identity` 是跨照片稳定但不需真实姓名的标签。可选 `smallFace` 用于按标注人员的定义统计小脸召回；未填写时，短边小于 96 像素的框按小脸统计。每张照片还可加 `tags` 场景标签，同一张照片可属于多个场景；建议覆盖拍摄年份、侧脸、低分辨率、合照和单文件夹样本，标签须为非空且不重复的字符串。

```json
{
  "schemaVersion": 1,
  "photos": [
    {
      "resourceId": "sample-0001",
      "path": "./photos/one.jpg",
      "tags": ["year:2024", "side-profile", "low-resolution"],
      "faces": [
        { "box": [120, 80, 42, 48], "identity": "person-a", "smallFace": true }
      ]
    }
  ]
}
```

运行 `python evaluate_people.py --annotations <清单.json> --models <cacheDir>/derived/ai/models --device cpu`；也可指定 `--device gpu`、`--limit-photos`、`--small-face-max-side` 与 `--output`。脚本对 quality-v2 运行当前方案，对 Buffalo_m 分别运行 640 全图快速路径（`overview`）和条件分块路径（`adaptive`），同一照片和标签可直接比较小脸召回、分组变化与额外耗时。模型文件只读，图片和特征不进入仓库。检测框与标注框按 IoU 至少 `0.5` 做一对一匹配，报告整体和各标签场景的小脸检测 precision/recall/F1、身份 pairwise 指标、分裂身份率、混合身份组率及 singleton 占比；分裂身份率以标注身份数为分母，混合身份组率以索引人物组数为分母。`buffaloMComparison` 汇总自适应分块相对全图路径的召回变化与耗时差。特征诊断包含检测脸进入特征索引的比例，以及最多 256 张匹配脸的跨照片同身份/异身份余弦分布；余弦仅用于区分度诊断，不代表身份概率。性能报告拆分模型加载、逐图推理时间、吞吐和 p50/p95；报告顶层的进程峰值工作集是宿主内存指标，GPU 显存峰值当前返回 `null`，需另用设备侧 profiler 测量。当前没有本机人工标注集，因此真实身份准确率、小脸召回和 Buffalo_m 分块收益仍待标注后验证；合成测试结果不能替代这些指标。

除标签场景外，报告还按拍摄年份（从照片路径推断）和脸部短边分档（`tiny`/`small`/`medium`/`large`）给出同样的分层指标，用于定位「哪一年、哪种大小的脸最容易出错」。`matchSuggestions` 描述的是另一层效果：待确认匹配有没有把同一个人的两个分组摆到用户面前。`trueDuplicatePairs` 是标注身份被拆进多个分组的对数，`surfacedDuplicatePairs` 是其中被摆到用户面前的部分，`duplicateRecall` 与 `suggestionPrecision` 是这一层的召回与准确率，`missedDuplicates` 与 `falseSuggestions` 逐条列出分组 ID 与照片资源 ID，可回到照片本身核对。`matchPolicyComparison` 用同一份检测结果再按旧复核口径评一次，给出当前口径与旧口径的差值。

`cmd/people-eval` 接受 `--match-policy current|legacy` 切换复核口径。`legacy` 复现扩大召回之前的规则：来源组只收 1～2 张照片，目标组要求至少 10 张脸且至少 3 张照片。评测报告不含原始照片路径与特征向量。

### 人物标注工作台

标注工作台是给评测准备数据的地方，不是人物修正的替代品。它与人物修正分开存放：标注只描述「这张照片里有哪些人脸、属于哪个匿名身份」，既不改写人物分组，也不改写命名、合并、排除与保留的决定，更不会修改原始照片。标注进度写在 `state/people-annotations.json`，人物修正仍写在 `state/people-<model>.json`。

样本从三处抽取：待确认匹配的来源组与目标组、只在合照中出现的组、锚点与中心相似度最低的低质量分组。抽样结果按顺序保存在本机，重新抽样才替换；标注者可以按顺序一张张标下去，进度不会因为重新抽样而丢失。

界面支持三种操作：给检出的脸指派匿名身份、在照片上拖动画框补检漏检人脸、选中一张脸后再画框以纠正检测框。身份由本机生成匿名 ID，用户只写编号或备注，不需要真实姓名。场景标签用于按拍摄情况分层：跨年龄、侧脸、低清晰度、大合照、逆光、遮挡。

导出接口 `GET /api/admin/people/annotations/dataset` 返回 `schemaVersion=1` 的标注集，与 `evaluate_people.py` 读取的格式一致。这组接口与目录管理、状态导出一样只允许回环访问：导出文件带本地绝对路径。标注数据只在本机保存，默认不上传，也不进版本库。

`AIJobService` 与扫描任务分开运行：扫描负责发布当前资源快照，分析服务只处理快照内的图片文件。`metadata`（EXIF/GPS）、`embedding`（Chinese-CLIP）、`ocr`（RapidOCR）与 `face`（YuNet + SFace）都通过 `AIAnalyzer` 注册并各自维护版本。全量任务重算全部图片，增量任务按资源 ID、大小、纳秒修改时间与模块版本筛出新增或变化项；带 `albumId` 的定向任务只从指定照片相册取得图片 ID，定向序列跳过与智能分组无关的 OCR。人物分析通过 `peopleEnabled` 默认关闭；明确开启后才允许手动、按序或每日启动 `face` 任务。人物页将已确认组和至少出现于 3 张照片、且有普通照片的组列为常见人物；少于 3 张照片的未确认普通组通过匹配建议端点人工检查，只在合照中出现的组通过合照候选端点分页检查。合照按每张照片的检测人脸数与源图归一化脸部尺寸分类：超过 20 张脸，或至少 8 张脸且中位相对脸部尺寸不超过图像长边的 4%。确认组不会被合照分类隐藏，搜索仍覆盖全部组。审查排序才会从已有特征计算组内锚点相似度、中心相似度与检测分数的 P10；候选匹配不会自动合并，质量统计和相似度不代表身份概率。OCR 文本和人脸框/特征写入既有分析批次；相似人脸接口只返回通过当前路径和文件指纹检查的照片 DTO，不对外暴露特征向量。每个结果仍由现有任务服务按 32 张一批提交、恢复与重试，不另设任务队列。

`SmartAlbumService` 只读取指定照片相册的直属图片，在 EXIF 拍摄时间、离线地点、现有人物候选和已有 Chinese-CLIP 向量上生成四类详细虚拟分组，再以这些分组作为证据生成精选主题，不移动或复制媒体。一级推荐至少 12 张且质量分不低于 0.82，按独立证据覆盖、场景凝聚度、来源相册重叠程度与名称新信息评分；仅有相似场景的候选不升级为推荐，人物候选需有场景支撑，每个来源相册最多保留一个人物起始的推荐。与来源文件夹近似整本相册的候选，只有名称补充文件夹信息且有多项证据或跨日活动支撑时才保留；10–20 张的整本相册不生成重复推荐。相邻拍摄段只有地点、人物或场景线索能串联时才合并。成员包含率达到 0.60 或 Jaccard 重叠达到 0.40 的候选只保留质量更高的一条；每本相册按规模限制推荐数。派生缓存键包含相册 ID、来源文件夹名称、维度、资源 ID 与文件指纹、相关分析记录版本和分组算法版本；不同相册使用不同缓存文件。时间使用可信拍摄时间并按间隔切段，地点按文件夹规模选择行政粒度并只输出地区名或 geohash 单元名，不向浏览器传 GPS，人物只取当前相册成员，场景以相互近邻、粗粒度语义标签与相似度门槛保守成组。名称、证据说明、质量分与成员摘要按需计算，媒体页在返回前再次校验当前相册成员、路径边界、普通文件与指纹。推荐组 ID 由文件夹和种子组稳定派生；刷新时依据成员重叠迁移用户改名/隐藏，若多项旧修改合并冲突则提示复核并保留原状态键。用户修改写入 `state/smart_album_overrides.json` 并包含在状态备份，分组成员只保存在可重建的 `derived/ai/smart-albums/`。每日计划的智能相册步骤遍历全库照片相册的四个详细分类和精选推荐，共五个维度，复用指纹匹配的派生缓存，只重建媒体或分析结果变化的分组。`SmartAlbumRefreshService` 把这次全库遍历做成后台任务：手动触发与每日计划共用它，同一时刻只跑一个，有进度、可取消，失败只回错误码不回本机路径。相册内空维度会指出所需分析模块，并可将该模块的增量任务限定到当前相册；人物任务要求先显式启用人物分析。计划页按当前所选模块提示可生成的详细分类，未选模块不会在智能相册步骤中隐式启动高耗时分析。

任务状态、每日计划与最后一次计划流程状态写在 `state/ai_jobs.json`，每 32 张图片提交一个批次检查点；批次结果使用同目录内的原子 JSON 文件，位于 `derived/metadata/<模块>/batches/<任务 ID>/`，可重建且与用户状态分开。结果文件先原子发布，再写检查点；启动时扫描结果批次并修复“结果已写、检查点未写”的崩溃窗口。任务恢复只从最近已提交的批次继续，未提交的尾批会重跑；`recoveredAfterRestart` 持久标记服务重启后恢复的任务，任务中心同时显示已提交批次与恢复状态。用户主动暂停的任务不会标成自动恢复。失败记录写入同一批次，错误仅含资源 ID、稳定错误码和脱敏原因。

「哪些图片已经是最新的」只有一份实现：`aiRecordIsCurrent`（`internal/services/ai_jobs.go`）比对既有结果的大小、纳秒修改时间与模块版本，并交给模块自己的 `RecordCurrent` 校验。任务开跑时筛选候选集用它，空闲时的规模核算也用它 —— 两条路径共用一份判据，预估出来的增量张数才与任务实际的 `planned` 对得上。

空闲时的规模核算由 `AIJobService.Estimate`（`internal/services/ai_job_estimate.go`）提供，经 `GET /api/ai/jobs/estimate` 暴露，只读、不建任务、不写状态文件。文件指纹清单由 8 个 worker 并发采集（stat 是 IO 密集的，与分析 worker 的 4 个上限分开），按媒体库 revision 缓存 30 秒；**任务开跑不复用这份缓存**，它必须用当下真实的 stat，否则文件刚被改过时会被误判成「已经是最新的」而跳过重跑。核算的 IO 全在任务状态锁之外，锁内只做内存里的计数。预计耗时取同模块历史终态任务（`completed` 与 `failed`）每张耗时的中位数，`elapsedMs` 与 `speedPerSecond` 不落盘，耗时由 `startedAt` / `finishedAt` 与实际分析张数重算；没有历史就返回空值，不给默认速度。

每个任务最多使用 4 个 worker；embedding 分析器把 Worker 并发限制为 1，保证同一进程只有一条 GPU 推理请求。暂停在批次边界生效；取消不提交当前未完成批次；退出将运行中任务恢复为 pending，暂停任务保持 paused。启动时自动恢复 pending；活动任务只有一个，断开 SSE 只释放订阅，不影响共享任务。每日计划使用服务本机时钟，初始时间为 03:00、默认开启扫描与智能相册刷新，AI 分析默认选择 metadata。计划状态与阶段落入 `state/ai_jobs.json`；到时依次等待扫描完成、把就绪模块的增量任务按顺序加入现有队列并等待终态、最后刷新所有照片相册的四类详细分类和精选推荐。计划运行时暂缓新的手动 AI 任务，避免分析与扫描交错；扫描失败会终止本轮，分析模块失败仍记录在独立任务历史中并继续后续步骤。未就绪模块不启动。错过前一计划日后启动时补跑一次，同一天只执行一次；异常退出留下的运行状态在重启后标为中断并补跑。

运行中的阶段依次报告 GPU 环境检查（GPU 任务）、媒体库等待、分析清单整理、首批模型准备和模块批量推理；首批推理可能包含 Python 模型冷启动。Worker 按 CPU 与 CUDA 各缓存一份 Chinese-CLIP，进程退出时释放；第一次使用另一种设备仍需加载一次，之后切换复用缓存。GPU OOM 自动回退时丢弃失效的 CUDA 缓存并把当前模型保存为 CPU 实例，避免后续误用不完整的 GPU 状态。任务 ETA 仍基于任务运行墙钟和已完成图片推算，包含首次模型加载及批次提交时间；对于很小的任务会偏粗，阶段标签可以区分准备过程，但 API 还不单独提供模型加载毫秒数。

AI Worker 使用独立 `backend/aiworker/.venv`（Python 3.11）。Windows/Linux 安装 PyTorch 2.7.1 + CUDA 12.6 与 Chinese-CLIP 1.6.0；macOS 使用 PyTorch CPU 版。RapidOCR 3.10.0 + ONNX Runtime 1.20.2 处理文字，OpenCV 4.12.0 + YuNet/SFace ONNX 权重处理人脸。Windows/Linux 使用 ONNX Runtime GPU 版，macOS 使用 CPU 版。Go 通过 stdin/stdout JSON Lines 调用并将 stderr 接入服务日志，Worker 常驻并复用 OCR/人脸模型。每个模块独立报告依赖与权重状态；缺失时任务中心不会把它显示为可运行。所有权重只从 `cacheDir/derived/ai/models/` 读取；RapidOCR 的 PP-OCRv6 检测/识别和 PP-OCRv4 方向分类模型位于 `ocr/` 子目录，启动时校验 SHA256，模型下载脚本固定到 RapidOCR v3.10.0 来源并校验 SHA256，不在服务启动时联网下载。新建的 embedding、OCR 和 face 任务默认强制使用 GPU；任务保存创建时的 `cpu` / `gpu` 选择，关闭 GPU 偏好后新任务使用 CPU。强制 GPU 不回退到 CPU，硬件不可用与推理失败分别进入任务错误码。Chinese-CLIP 遇到 CUDA OOM 时减半批量，单张仍 OOM 则将该图片记录为失败；语义搜索请求仍使用 Worker 的自动设备模式。搜索与建库推理共享同一串行 Worker。

Windows 上 Worker 将 CUDA DLL 目录加入进程 DLL 搜索路径和 `PATH`，避免 ONNX Runtime 找不到 PyTorch 附带的 CUDA/cuDNN DLL。RapidOCR 按需加载检测、分类和识别模型；GPU 推理后逐个检查已加载 session 的首选 provider，若实际回退到 CPU 则丢弃 GPU 引擎并记录 `gpu_inference_failed`，避免后续图片继续走 CPU。这项 session 检查参考 [LibrePhotos ONNX session helper](https://raw.githubusercontent.com/LibrePhotos/librephotos/dev/apps/backend/service/onnx_session.py)。GPU OCR 分类器批次为 16，CPU-only 分类器和 PP-OCRv6 识别器保持 6；识别批次16在当前 ONNX Runtime/CUDA 环境会触发 CPU 回退。

Worker 的代码分成两个文件：`worker.py` 是唯一的协议入口（JSON Lines 的读循环、请求分派与响应编码），`worker_imageio.py` 是与状态无关的共享解码实现 —— 人脸与 OCR 的「按上限解码」收成一份，两边的上限口径不同（人脸看长边、OCR 看像素总数），压缩比策略由参数给出。协议入口同时持有全部可变状态（已加载的模型、各模型的缓存、当前设备），评测脚本与测试可以直接替换其中的条目。

协议有两处硬性约定：响应必须原样带回请求 ID —— Go 侧按 ID 配对，对不上就把 Worker 当成失联杀掉并丢掉整批结果，因此单次请求失败不能拖垮整批；三处检测流程（YuNet、YuNet 图块合并、Buffalo_m）用同一份 NMS 与同一套重叠口径，同一批检测不能被两套口径各算一遍。

GPU 人脸任务最多用 4 个线程并行处理不同照片，同一 YuNet/SFace session 可由这些线程共享，返回项仍按输入顺序排列。首个请求的模型加载由锁保护，避免并发建库时重复创建 GPU session；CPU 人脸任务保持串行，因为 OpenCV 的 YuNet 检测器会逐图修改输入尺寸。

人脸任务有两个可切换配置：默认保留的 `quality-v2` 使用 YuNet + SFace，生成 128 维特征；`buffalo_m` 使用 SCRFD 2.5G + ResNet50，生成 512 维特征。Worker 将两者转换为相同的检测框、五点关键点与归一化特征数据结构，Go 任务快照记录所选配置和独立分析版本。Buffalo_m 使用官方 ONNX 输出解码、640 像素输入、0.5 检测阈值与 NMS；人脸对齐后由 ONNX Runtime 执行 ResNet50 特征提取。GPU 每个模型最多 4 个照片 worker，quality-v2 沿用原有并发策略。人脸输入最长边限制为 2048。GPU 用 640 像素窗口和 128 像素重叠扫描原图；CPU 用整张限尺寸图片检测。两种设备在图片最长边超过 640 时都会再跑一次等比缩小至最长边 640 的全图检测，补充 YuNet 文档所述约 10×10–300×300 训练尺度之外的近景大脸（[OpenCV Zoo YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)）；检测框与五点关键点映射回原图后统一做 NMS。脸分析版本包含检测流程版本，旧结果会在下一次增量人脸任务中重算。启动重算时，人物索引会暂时从上一版同特征空间记录恢复现有分组与纠错；新版结果逐批到达后再替换对应照片。

Chinese-CLIP 图像嵌入每次最多接收 32 张；常规图片最多 8 个线程并行解码和执行图像变换，超过 4MP 的非 JPEG 批次收敛到 4 个线程，再按输入顺序送入同一条 GPU 推理路径。GPU 初始推理批次为 32，CPU 为 8；CUDA OOM 时沿用减半重试，保持低显存显卡的适配。图像预处理会先应用 EXIF Orientation，再生成向量；该规则纳入模块版本，变更时既有嵌入会失效并按需重建。文本嵌入不创建线程池；图像预处理失败仍按单张记为 `image_unreadable`，不会中止同批其他照片。[LibrePhotos 为 OpenCLIP 提供动态批次 ONNX 导出](https://raw.githubusercontent.com/LibrePhotos/librephotos/dev/apps/backend/scripts/build_openclip_onnx.py)，并将方向归一化的大缩略图作为机器学习图像输入（[缩略图处理说明](https://github.com/LibrePhotos/librephotos/blob/dev/apps/docs/docs/development/contribution/backend/thumbnails.md)）；这里先在原图预处理阶段修正方向，保留现有 Chinese-CLIP 权重与运行时。

向量以 512 维 Float16 保存在 `derived/ai/vectors/shards/`，每片有 JSONL 元数据与 SHA256，manifest 原子发布并标记已压实分片；元数据只含资源 ID、文件指纹、模型版本和片内位置，不保存文件路径。应用启动时将 Float16 shard 装入内存，完整校验哈希后才用于检索；模型/索引版本不兼容时重建派生索引。索引增量追加，累计 128 个未压实 shard 后由独立后台压实，每片最多 512 条；达到压实门槛后不因已有分片数量重复排队。检索将查询向量归一化一次，用半精度解码查表和有界 Top-K 堆代替逐条解码后的全量排序。Windows RTX 3060、本地 Go 基准 100,000 向量、512 维、31 次测量：p50 从 193.2 ms 降至 73.3 ms，p95 从 222.3 ms 降至 79.8 ms，每次搜索分配从约 2.4 MB 降至约 2.5 KB；索引堆约 129.8 MB。复现命令：`go test ./internal/services -run '^$' -bench '^BenchmarkVectorIndexSearch100K$' -benchtime=31x -benchmem`。

OCR 额外维护 `derived/ai/ocr-search-index.json` 倒排索引，索引项仅存 OCR 词元、模块版本和文件指纹，启动时从已提交的 OCR 批次核对并修复，任务批次提交后增量更新。查询会归一化全半角、CJK 空格/断行与中文标点，并在长中文短语上允许一个受限的常见混淆字或插入/遗漏；最终仍与当前 OCR 原文核验，精确结果排在近似结果之前。中文 OCR 回归集 8 个正例和近似负例，改动前精确率/召回率为 0/0，改动后均为 1.0（8/8 正例、0 假阳性）；该数字只代表固定合成文本夹具。向量查询支持 OCR 优先级，API 的 `matchReasons` 说明语义、以图、文字精确或近似命中。

人物服务只使用当前选中模型版本的人脸记录，并按其 128 或 512 维特征空间独立构建 HNSW 与聚类中心，禁止跨模型比较。每张脸先用 HNSW 取得最多 128 个近邻组，再按当前组中心精确重算余弦相似度。中心门槛为 `0.520`；与组内最多 8 张高置信度代表脸之一的余弦高于 `0.720` 时直接归组，若与至少 2 张不同照片的代表脸余弦高于 `0.580` 也可归组。模糊匹配只看脸部特征，不再用 CLIP 整图语义作为身份证据；同一组仍限制同一照片最多一张脸。多个独立脸部匹配用于补回姿态变化导致的漏组，同时避免单个相似场景推动归组。聚类阈值沿用当前质量版启发值，Buffalo_m 尚无本机标注集校准；遮挡、姿态变化或相似人脸仍可能误拆或误并。输入按资源 ID 与脸序号排序，索引使用固定随机种子，按稳定的人物 ID 处理同分候选；近邻搜索是近似的，可能漏掉匹配组，因此结果可编辑。不设比较次数或人脸总数上限。人物列表在内存中按当前照片目录汇总唯一照片数，只返回照片数最高的 50 组；用有界 Top-K 选择避免对全部分组排序，列表读取不逐张访问媒体文件。照片数相同时按封面资源 ID 与人物 ID 稳定排序；详情合并选择器以受限搜索获取目标，不向浏览器发送全量分组。详情媒体接口只聚合目标组，并把路径与文件指纹校验限制在当前分页。人脸分析仍需覆盖全库，才能准确计算最多照片的候选组。配置的 FFmpeg 可用时，HEIC/HEIF 人脸分析先转为最长边 4096 的临时 JPEG；worker 分析临时图，源文件路径与指纹仍按原图复核，批次结束后清理临时目录。分析结果按批次进来时只做增量：同一张照片重新分析过的旧人脸先去掉，新的人脸再并进现有分组，分组编号与用户改过的分组都保持不变。增量攒出来的分组与批次到达顺序有关，所以任务收尾时整体重建一次 —— 重建按资源 ID 与脸序号排序，并用新旧组的脸重叠迁移命名、隐藏和手动分配；任务期间被换掉的人脸若属于用户改过的分组，仍然留在那个分组里。若重建会合并多个已有人工修正的组，或拆分一个已有人工修正的组，则保留原分组映射，直到用户显式合并或拆分。聚类缓存每组归一化中心，避免每次比较临时重算。名称、隐藏状态与纠错映射写入 `state/people-<model>.json`；`derived/ai/people-index-<model>.json` 保存资源 ID、指纹、记录哈希、脸部框与分组引用，不复制特征向量。启动时若记录哈希和分组算法版本一致，复用脸到组的映射并重建中心和代表脸；HNSW 图延迟到新脸到达时构建，人脸分析结果变化时才重新聚类。语义结果采用当前有效资源的精确余弦排序，纯 OCR/结构化结果按资源 ID 稳定排序；年份筛选使用当前 EXIF 拍摄年份，GPS 筛选复用既有 geohash 精度 5 地点 ID，人物、收藏与精选条件叠加在同一候选集合上，媒体库快照与文件指纹在返回前再次校验。当前不引入数据库或外部推理服务。

任务快照分两类字段：事实与派生。`results`（按解析状态分类的计数）与 `fields`（按字段统计的产出）是事实，随每个 32 张的批次原子提交并落盘；重启时按批次文件重放，与失败计数走同一条恢复路径。`planned`、`completed`、`estimatedRemainingMs` 与速度是派生值，每次快照按落盘的计数重算，不写入状态文件 —— 写进去就等于把某一刻的估计当成事实。已注册的分析模块清单由后端给出，客户端不维护第二份模块名表。

任务中心的界面拆成四个页签：运行（当前任务的进度、读数与控制，空闲时是开始分析的入口）、每日计划（开关、时间、扫描/分析/智能相册任务选择与人物开关）、任务记录（历史任务与失败项）、本机存储（派生缓存占用、AI 模型权重与各模块产物、相对路径与本机绝对路径）。等待队列作为「运行」页签的附属面板贴在它下面，始终显示并明确呈现空队列状态。状态面板与队列之间是「智能相册分组」面板：增量更新与强制重建两个入口跑全库刷新，面板显示当前相册、维度与进度，可中途取消；生成结束后首页汇总与相册页的分组摘要一起失效重读。每个页签独占整幅宽度，宽屏的宽度用在卡片内部（运行面板左右分栏、每日计划模块与人物开关左右分栏、本机存储两卡并排）。任务数据层收在 `hooks/useTaskCenter.ts`，存储数据层收在 `hooks/useStorage.ts`，面板在 `components/tasks/`；路由组件只排版。分析模块用芯片列出（`components/tasks/ModuleChips.tsx`），互斥选项用分段控件（`components/common/Segmented.tsx`），两类控件在各页共用同一套语义与键盘行为。单项启动和“按序启动全部任务”都复用 `AIJobService` 的持久队列；全部任务固定按 metadata、embedding、OCR、人脸顺序入队，缺少依赖或模型的模块跳过，前端在每项终结后刷新活动任务以跟上下一项，等待中的任务按执行顺序排列显示。失败项按「错误码 + 原因」在前端分组，同一原因的几百条路径折叠起来只留计数，展开才列路径。进度分母是本次任务实际要处理的张数（`planned`），不是整库规模：增量任务里整库大部分文件已经是最新的，拿整库当分母会让进度一上来就接近满格。

空闲时先给数字再给按钮：运行页签在头部条与主体之间放一条「本次规模」（`components/tasks/TaskEstimatePanel.tsx`），把增量与全量两种口径的张数与预计耗时并排列出，当前模式那一行高亮。四个模块 × 两种口径由一次核算带来，切模式与切模块都不重新请求。模块与模式的选择态放在 `hooks/useTaskCenter.ts` 而不是组件里 —— 规模表、按钮上的张数说明与真正发出去的启动请求必须读到同一个 mode，分开存必然漂移。任务进入终态、用户清空历史、媒体库重新扫描之后都要让核算失效重算。每日计划按增量口径给出「预计下次运行」的张数与耗时。

本机存储信息集中在任务中心的「本机存储」页签：媒体派生缓存的占用与清理读取既有的 `GET /api/cache/stats`，AI 模型权重与各模块产物的占用读取 `GET /api/storage/usage`。设置页只保留外观与导航、阅读偏好、服务端配置、状态备份和关于，按四个页签分组（`utils/pageTabs.ts`）：界面（外观 + 导航）、阅读、数据（媒体库索引 + 备份与恢复）、服务端；关于是页脚一行，不占页签。每个页签独占整幅宽度，按自己的内容排（`styles/global.css` 的 `.settings-grid` / `.settings-grid--aside` / `.settings-card`），服务端那七组面板自带标题条排三列，一组一块，不再是白卡里的白卡。

导航只有一条竖轴：应用级在左侧栏（`components/layout/Sidebar.tsx`），侧栏分「浏览」与「本机」两组。页面级分区不在侧栏挂第二层菜单 —— 它由页面内的页签条承担（`components/common/PageTabs.tsx`，`role="tablist"` / `role="tab"` / `role="tabpanel"`，方向键在页签条内切换，不注册为全局快捷键）。页签清单只有一份（`utils/pageTabs.ts`），页签条、页面面板、浏览器标题与侧栏上的当前页签名都从它出。页签的 id 进 URL 路径段（`/settings/data`、`/tasks/plan`）：`/settings` 与 `/tasks` 重定向到缺省页签，不认识的页签由 `resolveTab` 回落并 `replace`。切页签不重挂页面 —— `utils/path.ts#pageBoundaryKey` 把这两页的子路径折叠成同一个错误边界 key，面板第一次打开后保留挂载（用 `hidden` 藏起来），服务端配置的草稿、备份预览与任务记录的筛选因此不丢。侧栏在窄屏是抽屉；侧栏自身可滚动，窗口不够高时不会把底部入口挤出侧栏。

侧栏入口的清单也只有一份（`utils/navEntries.ts`）：侧栏按它渲染，设置页的「导航」分区也按它逐项开关。哪几项显示由服务端偏好 `hiddenNavItems` 决定（存的是生效的隐藏清单），`hooks/useNavVisibility.ts` 读它并给出可见性判断；偏好没读回来时用前端默认清单兜底，与服务端默认值一致，所以不会出现先全显示再收掉的闪动。工作台首页固定显示，收起它那一侧的侧栏就空了。

**按钮上的描边由全局规则决定。** `styles/global.css` 里按钮只清宽度（`border-width: 0`）不动 `border-style`：Tailwind 的 `border` / `border-b-2` 只改宽度，样式一旦被重置成 none，按钮上的描边会整条消失。区域层次因此靠「白卡 + 浅色标题条 + 发丝线」建立，不依赖按钮描边。

存储信息分两层给。`GET /api/storage/usage` 经过普通访问门禁即可访问，路径一律相对缓存根目录（`derived/metadata/ocr`、`state/ai_jobs.json`），局域网客户端也能看；`GET /api/storage/paths` 仅限回环访问，给出缓存根目录、工作目录、配置文件、Python 环境与各权重文件的绝对路径。完整路径不进入浏览器持久 store，也不向局域网客户端开放。任务记录展开时按需读 `GET /api/ai/jobs/:jobId/output`，给出这次任务自己的批次目录与占用；折叠状态不发起请求。

EXIF 解析器保存拍摄墙上时间、朝向、相机信息和 GPS 附属字段。缺少 EXIF/不支持格式属于正常解析状态，损坏文件计入单项失败。EXIF 日期只作为元数据返回；相册业务日期仍维持 `filename > folder > modified`，不会被 EXIF 改写。

## EXIF/GPS 与离线地点地图

地点页同时使用两套本地数据：旧的 Geohash 精度 5 分组为语义筛选和地点照片分页提供稳定 ID；地图接口则读取嵌入的省、市、区县边界，将有效 GPS 匹配到省份及最细可用的下级区域（无更细边界命中时退回城市），分别统计照片数。每次匹配都从当前 catalog revision 重新筛选元数据，要求资源仍是图片、路径通过 `PathValidator`，且大小与修改时间戳仍匹配；地图响应只含行政边界和聚合数量，不返回原始照片坐标或文件路径。唯一的例外是点云端点 `GET /api/locations/china/points`：它给的是照片位置的**粗网格聚合**，见下面的「点位与网格」。EXIF GPS 默认按 WGS84 处理并转为边界使用的 GCJ-02；显式标记为 GCJ-02 的坐标不重复转换，未知 datum 不参与地图匹配。

离线边界文件 `backend/internal/services/geodata/china-admin.geojson.gz` 由 AreaCity-JsSpider-StatsGov `2025.251231.260403` 版的 `ok_geo.csv.7z` 转换而来，数据更新于 2026 年 4 月 3 日。AreaCity 说明该版整合国家地名信息库 2025-12-31、腾讯地图行政区划 2025-11-19，并以高德行政区划和边界为主要来源；边界坐标系为 GCJ-02。上游将省市区三级边界包列为免费开源，乡镇边界是另一个付费数据包，本项目不使用它。上游仓库没有为该边界文件单独列出数据许可证；保留来源与版本记录，商业使用或再分发前应向上游及来源方核实授权。地图渲染与坐标匹配不发起外部地图、反向地理编码或 AI 请求。

数据更新时从 [AreaCity 发布页](https://github.com/xiangyuecn/AreaCity-JsSpider-StatsGov/releases/tag/2025.251231.260403) 下载 `ok_geo.csv.7z`，解压后运行 `python scripts/update_china_boundaries.py <ok_geo.csv路径>`。转换器仅使用 Python 标准库；它还原六位区划码、移除与父级同名同形的占位边界，并将其下级改挂到真实父级。当前下载包 SHA-256 为 `675C3E9B8DEC6444994D3EF53259A145304F6A957DB8A5E601E55C0B9E61E21A`。当前内嵌文件包含 3,214 个要素：34 个省、335 个城市、2,845 个区县。上游 3,209 条区县记录与 392 条城市记录中，台湾的 378 条区域边界为空而未嵌入；43 条重复层级被折叠。生成文件约 53.4 MiB，解压后的 GeoJSON 约 173.1 MiB，SHA-256 为 `05C2693D8FFBA8B6161E65470A7874AF17DBDD2EC86878F16C86721160FA0E93`。乡镇边界不包含在这套数据中。绘图用的轮廓文件由 `python scripts/simplify_china_outline.py` 从这个文件生成，不必重新下载上游数据。

上游本次发布说明指出，新疆和田新设的和康县、和安县尚无高德边界而未收录；它还更新了重庆两江新区相关区划。数据也不覆盖雄安新区等多数行政管理区。若以后接入乡镇边界，需要扩展当前只接受省、市、区县三级的转换器、后端层级匹配和地图下钻；本项目不包含上游单独标为付费的乡镇边界包。

**全国到区县逐级下钻。** 地点页按父子关系展示全国、省、市、区县；直辖市及同名省市重复边界会折叠，省直辖县级区域直接挂在省下面。各级照片数向父级汇总，因而城市计数包含它下辖区县的照片；当前区域自身有照片但没有任何下级边界命中时，`unmatchedAreaPhotoCount` 标出这部分数量。台湾的省级轮廓存在，但没有可用的城市和区县几何，因此按叶子处理。

**匹配与绘图用两份边界数据。** 点位判定要全精度：照片必须落在真实边界内，边界差几十米就可能归错区。绘图只要形状：全国图上省界偏移 0.01°（约 1.1 公里）看不出来，但下发全精度顶点是 18 MB 的 JSON。因此内嵌两份文件，来源同源、用途分开：

| 文件                                     | 用途     | 体积                       |
| ---------------------------------------- | -------- | -------------------------- |
| `geodata/china-admin.geojson.gz`         | 点位匹配 | 56.0 MiB（解压 181.5 MiB） |
| `geodata/china-admin-outline.geojson.gz` | 绘图     | 5.0 MiB                    |

轮廓文件由 `python scripts/simplify_china_outline.py` 从匹配文件生成（只用 Python 标准库，Douglas-Peucker 简化加按层级分档的容差：省 0.01°、市 0.004°、区县 0.002°；生成时关掉文件名与时间戳，同样的输入产出同样的字节）。它不改变匹配文件，只是把同一份数据简化成能画的样子。两份文件的区划码、层级与上级必须一一对应，由 `china_boundary_outline_test.go` 的交叉校验守住 —— 运行时不做这项校验，那会把 6 秒的匹配索引加载拖进绘图端点。

**几何按需下发，统计与几何分开。** 统计端点（`/api/locations/china`、`/api/locations/china/regions/:adcode`）只给数字，几何由 `GET /api/locations/china/geometry/:level` 单独下发，且只给当前视图需要的层级：全国给省，进入省给该省的市，进入市给该市的区县。整份轮廓不下发。改造前全国那一次请求是 18,013,977 字节的 JSON，改造后是 12,206 字节的统计加 265,877 字节（gzip）的省图。

**轮廓另有一条按区划码取的路。** 地图要画的是「去过的那些地方自己的形状」，而它们的父级在前端推不出来：直辖市的区县没有市一级（`310104` 直接挂在 `310000` 下），省直辖县级市在市级粒度里会卷到省，同一个粒度的地方列表里还混着不同层级的条目。因此 `GET /api/locations/china/geometry/features?adcodes=…` 直接按区划码查表（轮廓索引里本来就有 `byAdcode`），不必绕那层推导。实测体积：22 个市约 88 KB（gzip），48 个区县约 300–400 KB。

进程启动时在后台预热匹配索引：它有 797 万个坐标点，加载要 6 秒、常驻约 1.4 GB，放着不管的话第一个打开地点页的人要等这 6 秒。轮廓索引小两个数量级（77 万个点、解析 0.6 秒以内），整份常驻。匹配结果按 `(catalog revision, 分析记录版本)` 缓存，重复查询不再重跑整库点位判定；边界匹配用纬度分桶缩小每次点在多边形检查的边集合。分析记录的版本号由 `AIJobService.RecordsRevision()` 给出，记录增删改时递增，缓存因此不会给出过期计数。统计端点的 ETag 用匹配文件的内容指纹（sha256 前 8 字节）；绘图端点的 ETag 只用轮廓文件的指纹并带长期缓存 —— 几何不随媒体库变化，不必因为换了张照片就重下。

### 点位与网格

行政区匹配答得出「落在哪个市」，答不出「具体在哪儿」——后者要靠照片自己的坐标。匹配阶段本来就算出了 GCJ-02 的经纬度（点位判定要用），用完就丢；现在留住它，画在地图上。

**点位只以网格聚合下发。** 一格是一段约 1 公里到 50 公里的范围，格里的照片可能横跨一条街，也可能是一整个景区。响应里只有「这一格在哪儿、那儿有多少张照片」，没有资源 ID、没有路径、没有单张照片的经纬度。这是一次有意的口径放宽，边界写在这里：

> 服务端手上本来就有比 0.01° 更细的位置（它拿来做点位判定），但**对外给出的最细粒度是 0.01° 一格**。同一台服务器本来就通过媒体接口提供这些照片本身，网格化只是把「连续坐标」降成「格点计数」，不新增一类信息。

格边长只认六档（0.01 / 0.02 / 0.05 / 0.1 / 0.2 / 0.5 度）：它是「画多细」的档位，不是一个连续参数。白名单让前端能按画布大小挑档 —— 地图只有几百像素宽，几公里的一格在画面里不到一个像素，点会糊成一片噪点，因此足迹页固定用 0.2 度这一档。格数超过 4000 时服务端自动调粗，`cell` 里回报实际生效的那一档。

格心取 `floor(lon/cell) * cell + cell/2`，**不是照片坐标的平均值**：平均值会把点拉回真实位置，格心不会 —— 一格里到底有没有照片，地图上看不出来，也不该看出来。

时间过滤与其它端点不同：**没有可信拍摄时间的照片一律保留**。它们有真实位置，只是没法判断在不在区间里；一并丢掉的话，一张没设时钟的照片就会让整张地图空掉。它们在每格的 `untimed` 里单独计数。

### 时间维度：三种时间，只用一种

地点页的轨迹叙事只用 **EXIF 拍摄时间**（`dateTimeOriginal`）。库里有三种「时间」，各管各的，不混用：

| 口径           | 来源                             | 用途                                 |
| -------------- | -------------------------------- | ------------------------------------ |
| 文件夹名年份   | 目录名里的 `19xx/20xx`           | `/photo/years/:year` 年份墙          |
| 相册业务日期   | `filename > folder > modified`    | 相册在时间轴上的位置                 |
| EXIF 拍摄时间  | `dateTimeOriginal`               | **地点页的时间轴、轨迹与到访**       |

EXIF 的 `dateTimeOriginal` 通常不含时区，因此保留相机记录的墙上时间，按**拍摄地的当地日期**比较 —— 这正是「我在杭州待了几天」这种叙事的口径；接口不声称给出绝对时刻。

**可信性只看解析结果，不看文件时间。** 解析失败、年份早于 1990 或晚于当年加一的照片，时间标记为不可信：它们照常计入空间统计，但不进逐月分布、轨迹与到访，界面如实给出这部分的数量（`untimedPhotoCount`）。不用文件 mtime 校验 —— 照片常是事后拷进库的，mtime 与拍摄时间能差出几个月，拿它当基准会误杀大量正常照片。

**时间索引在缓存里建一次，区间在读取时过滤。** 匹配阶段已经反序列化了 `ImageMetadata`，多解析一个 `dateTimeOriginal` 不带来额外 I/O。匹配结果里的照片按拍摄时间升序存放（时间不可信的排在末尾，仍按相册序），缓存键**不包含**请求的时间区间 —— 区间过滤发生在读取时，扫一遍缓存里的切片即可。这样不会出现「缓存里只有某一年的数据」这种错配，缓存也不会因为用户换时间区间而反复重建。请求级的时间区间只进入 HTTP 的 `ETag`，换区间后旧响应不会命中 `304`。

**到访按日历日切分，阈值是量出来的。** 同一区域的照片按拍摄时间排序后，相邻两张的**日历日间隔 ≤ 2 天**算同一次到访，超过则另算一次；列表和照片墙共用同一个切分函数，两边不可能对不上。按日历日而不是按小时，是因为「晚上八点和第二天早上八点」这种跨夜行程在人看来是一次。2 天这个阈值来自本机库的实测：同地点相邻照片的日间隔在 1 天 328 次、2 天 132 次、3 天起断崖式下跌到长尾，≤ 2 天合并、> 2 天另算正落在拐点上。阈值写成常量 `chinaVisitMaxGapDays`，修改需同步界面说明。

**轨迹的停靠点是行政区，不是照片。** 停靠点 = 连续落在同一区域的一段照片，粒度跟当前地图下一级走（全国＝省级，省＝市或省直辖区县，城市＝区县）。照片匹配到最细的可用区域，再向父级汇总；城市地图的轨迹因此落到区县，省地图则落到市或省直辖区县。后端只返回停靠点的**区划码与名称**，折线由前端用区域几何的质心连出来 —— 这样响应里依然没有任何照片经纬度。相邻停靠之间间隔超过 2 天就不连线，否则相隔两次出行的照片会被画成一条横跨半张图的假路径。



## 媒体管线

### 图片、缩略图与预览

- 缩略图采用内存 LRU 与磁盘 JPEG，源版本、尺寸和编码版本参与缓存键。读锁覆盖生成与查询，重配和清理使用写锁。
- 渲染图按固定宽度阶梯分档（320 / 640 / 1280 / 1920 / 2560 / 4096，见 [rendition.go](../backend/internal/services/rendition.go)）：请求宽度向上对齐到档位，档位进缓存键与 ETag，换档就是换一份产物。渲染不裁剪，各档宽高比一致，前端才能用 `srcset` 让浏览器自选档位。
- 内容版本号形如 `<mtime_ns>-<size>-r<算法版本>`，由源文件 stat 得到。媒体列表 DTO 带出版本号，前端把它拼进渲染图 URL；服务端比对一致时回 `immutable`，浏览器长期缓存，重复打开页面不再为图片发请求。
- 派生 ETag 为 `"<版本号>-<档位宽度>"`，不再对响应字节做哈希：条件请求只需一次 stat 加一次字符串比较，判定提到生成之前，冷缓存上的 304 也不必解码。
- 坏文件要标出来，别让用户对着破图图标猜。判定分两处：尺寸服务读图片头失败当场标 `undecodable`（需要服务端转换的 HEIC/HEIF/TIFF 不算坏）；图片头能读、像素数据却是截断的，只有真正解码一次才暴露 —— 渲染路径解码失败时回调尺寸服务补记，标记跟着文件走，文件被替换后判定作废。尺寸缓存早于这个标记，磁盘上的旧记录按「宽高都是 0 就是读不出图片头」补判，不必让整份缓存作废重探。
- 并发同时受 `min(12, NumCPU)` 和 192 百万像素预算限制；大图先 Box 预缩放到目标约两倍，再 Lanczos，不能只按图片张数估计解码内存。
- 像素预算闸门是加权信号量，容量就是预算本身：一次申请超过容量的权重会永远阻塞，把整条渲染链路（连同 HTTP 请求）一起挂死。因此权重永远压在预算以内，超过预算的大图（拼接全景能到 277MP）改走 ffmpeg 按目标宽度缩放后再解码，内存有界；ffmpeg 不可用时才退回进程内解码。本机实测：一张 6184×44767 的全景把重建任务卡在最后一项，修复后同一张图 3.9 秒出图，峰值内存约 1.2GB。
- HEIC/HEIF/TIFF 通过可选 ffmpeg 转换，整图转换与缩略图缓存分开。工具缺失或失败返回不支持格式，前端提供占位与说明。
- 连续阅读使用按目标宽度缓存的 `/api/previews`，单张/双张使用原图；预览规则与响应字段在 API 维护。
- 前端所有渲染图走 `components/common/RenditionImage.tsx` 一个出口：按槽位宽度与像素比选档，给出 `srcset` 与 `sizes`。照片模式的大图预览不走 `srcset`，而是按舞台尺寸与图片原始比例算出实际显示宽再乘像素比与缩放倍数取档 —— 视口宽不是显示宽，照视口宽要图会命中 4096 档（服务端对更窄的源图原样返回原图），一张 3.7MB 的原图就为了看 788 像素宽的一屏被整个拉下来。舞台尺寸用 `ResizeObserver` 量，量到之后才发请求，避免先要一张再改 URL。
- 视频封面优先 ffmpeg（同文件合并、全局最多两个任务），按视频流时长定位、短视频取片头，无帧时从片头重试。等比缩小、不放大、不补边；没有服务端封面时浏览器通过 Range 抽帧并回传。
- `useVideoCover` 的一次 effect 拥有探测、抽帧、上传整条链，切换/重试/卸载均取消并忽略迟到结果。探测 20 秒、抽帧 30 秒期限包含挂起请求；完成释放媒体元素、canvas、网络监听和计时器。

### 缓存重建任务

`internal/services/cache_rebuild.go` 的 `CacheRebuildService` 在后台重建派生缓存：枚举库快照里的相册与媒体（只在本机内部用绝对路径），按所选范围（缩略图 / 预览图）生成对应档位，video 不参与（ffmpeg 抽帧与转码代价另算）。任务状态机与 SSE 订阅复刻扫描任务的做法：终态事件后关闭连接。运行期间每 500ms 推一次进度快照 —— 逐项推太密，不推进度条就十分钟不动，看着像卡死了。

前端 `components/tasks/CacheRebuildPanel.tsx` 发起任务（随派生缓存一起收在任务中心的本机存储段），`hooks/useCacheRebuild.ts` 订阅 SSE，`store/cacheRebuildStore.ts` 持有 jobId 与进度 —— 只持久化 jobId，进度每次连接重新获取。切走页面再回来，任务仍在跑，进度接得上。

### 视频元数据与转码

`VideoInfoService` 优先 ffprobe JSON，缺失或失败则解析 ffmpeg 输入头；工具检查与探测均有超时，超时不缓存部分输出。成功摘要按规范化路径、大小、纳秒修改时间缓存到最多 512 项内存 LRU，同指纹 singleflight，失败可重试。单条/批量接口共用 DTO 与当前路径校验，批量保持顺序和逐项错误。

视频发送按“按需转码 → MP4 faststart remux → 原文件”选择。MKV/AVI/3GP 等浏览器无法使用的容器、冷门编码按需转 H.264 + AAC；moov 在末尾的 MP4 可仅 remux。工具不可用时降级到后续管线。

- faststart/转码缓存只命中非空普通文件，拒绝自身链接、目录和空文件；选择后再次复核。生成写目标目录的独占临时文件，成功并复核后原子发布，失败只清理本次临时文件，不删除占位目录或无关条目。
- 转码任务键含源路径、大小、纳秒修改时间与 profile；同版本去重、全局限流。新请求看到新版本时取消旧任务，启动与发布前再比指纹；被替换任务仍登记待回收，退出等待新旧 worker。
- 状态查询与订阅共用当前版本状态，磁盘有效缓存优先于旧进度/失败。仅活动任务保留订阅，其他状态发送完整终态并关闭；进度、终态、通道关闭与取消由同一任务锁串行保护。
- 大小和修改时间均未变化的内容覆盖不在指纹检测范围内；一键全清可重置内存元数据代次，使旧探测无法回填新缓存。

### 发送与浏览器生命周期

原图与视频共用 `serveMediaFile`：每响应独立打开最终文件，以同次 `f.Stat` 得到类型、长度、mtime 与 ETag；完整或单段 Range 流式发送，完成、断连、HEAD、304 与发送前错误均释放句柄，不缓存整段媒体或旧文件句柄。外部原地写入不构成事务隔离。

缓存协商要求浏览器重新验证，源校验先于条件请求；弱比较、If-Range 强校验与错误码集中在 API。播放/抽帧另外使用随机 `playback` URL 标识隔离同页解码缓冲：同次播放与 Range 保持地址，切换、重试、转码完成生成新地址；标识不参与鉴权、服务端任务键或持久活动。

`state/backups/` 保存用户手动恢复前的备份，不属于派生缓存，不参与缓存清理。对外只给相对缓存根目录的路径；绝对路径由回环保护的本机接口单独提供。对外备份仅使用资源 ID；另存的内部封面映射仅供本机恢复旧状态，不对外下载。人物修正备份包含两套模型各自的名称、隐藏状态与人工分配，不包含向量或模型产物。

派生缓存的写入攒批：媒体尺寸探测出的记录先在内存里排队，一页媒体处理完再一次性写盘并刷一次。逐条刷盘的话，一页两百张照片就是两百次 fsync —— 实测冷缓存下翻五页照片流要 1.8 秒，攒批后 0.55 秒。攒到一定量会自己落盘，调用方忘了刷也不会把内存吃满。

启动只读写当前分层布局，不读取、移动或删除旧顶层状态。偏好部分更新在同一写锁内读改写并原子落盘，避免并发修改主题时覆盖收藏/历史；高频活动独立文件，批量活动校验后一次写入。归一化后业务字段相同的活动保留原时间与版本，整批无变化时跳过复制、排序和落盘；有效变更仍先原子写盘再发布内存。

状态备份由 `StateBackupService` 组装偏好、活动与封面快照。预览提供状态摘要，导入时在各 store 锁内比较并原子提交；偏好相关类别在同一文件内合并，跨文件逐类报告结果，不宣称全局事务。封面存储先落盘再发布内存，写盘失败不污染当前视图。设置页备份面板只在组件内存中保存所选文件与预览，离开即释放；写入确认后刷新失败仍保留完成报告。

后台维护在启动及每小时运行，以 `os.Root` 限制删除在五类派生目录内，仅处理哈希命名的完整普通文件，不跟随链接、不进入 `state/` 或处理临时文件。按年龄与容量从旧到新清理，十分钟内的新文件保留，因此容量为软上限；`cacheMaxSizeMB: 0` 只关闭容量淘汰。

SIGINT/SIGTERM 触发停止接收连接、取消扫描/转码并强制刷新扫描缓存；HTTP 等待最多 5 秒，后台清理使用 10 秒退出窗口，维护任务也取消并等待结束。

## 前端状态与异步写入

### 临时选择与批量操作

`selectionStore` 仅保存至多 1,000 个待操作 ID 与少量选择摘要，不持久化。App 按路由与搜索/视图/年份/最少图数维护作用域；改变作用域清空选择，排序和追加分页保留。列表网格的选择模式使用独立复选卡片，避免星标、导航和选择动作竞争；“选择已加载项”不隐含全库选择。提交期间固定清单并禁止重复操作，跨页面的迟到确认仍更新查询缓存，但不清空新的作用域。收藏与已读写入使用已有 Query 状态，不增加长期媒体数据副本。

照片侧另有一份临时选择（`photoSelectionStore`）：照片墙与精选页勾的是「这一张」，
条目形状与相册选择不同（要带文件名与所属相册才能做并排对比），混在一份选择里
两边都别扭。它同样不持久化，作用域是相册 ID 或精选页。

精选本身只有客户端一份真相：`usePicks` 缓存精选的文件 ID 集合，它跨相册、跨页面
共享，因此在任意一处加入精选，照片墙、精选页与大图预览里的同一张照片会同时更新 ——
不必去改各个列表自己的缓存。写入先改本地集合（界面立刻响应），服务端确认后再取
一次权威结果；写失败退回原样，界面不停在服务端并不认可的状态上。服务端在媒体项上
另带 `picked` 标记，集合尚未回来时用它先把状态画出来。

### 工作台模式

工作台模式（`appMode`）就是目录的内容属性（`contentKind`）：`photo` / `comic` 两档互斥，没有不过滤的第三档。属性写在配置里（`mediaRoots[].kind`），目录下的相册与集合在发布时一并继承，没有单本相册的归类动作。服务端记住上次用的是哪一侧（`Prefs.appMode`，`state/web_settings.json`），它只是**落地页偏好**；当前在看哪一侧由 URL 路径前缀决定。

- 模式决定列表呈现哪一半，也决定相册点开进照片墙还是阅读器：照片工作台只列照片目录的相册，漫画工作台只列漫画目录的相册，两套菜单与措辞各自成套。
- 服务端列表接口的 `kind` 查询参数（`photo` / `comic`）必填，缺失或非法返回 `400 invalid_kind`：子节点、未读、随机、标签、标签相册与搜索按目录属性过滤。集合继承所属目录的属性，因此同样参与过滤——漫画目录下的集合不会出现在照片工作台里。它的 `albumCount` 恒为全部后代，但集合的所有成员都在同一媒体根（同属性），所以这个计数天然按侧，无需再拆一份。manifest 的 `albumCount` 是全库总数，另给 `photoAlbumCount` / `comicAlbumCount`，集合同理有 `photoCollectionCount` / `comicCollectionCount`。
- 过滤发生在分页之前：发布时预切好的有序切片按属性筛成子序列，游标里的偏移是过滤后列表的偏移。属性进游标作用域，跨属性复用被拒绝为 `invalid_cursor`。
- 未读/在读派生按 `(catalogRevision, activityRevision)` 缓存，缓存与属性无关，属性过滤是请求期后置筛选。未读下标只收漫画相册：照片目录下的相册不记录阅读进度，没有「未读」这个概念。
- 列表页的筛选状态在地址里：`q`（关键词）、`sort`（排序）、`min`（最少图数），首页另有 `view`（视图）与 `year`（年份）。链接可以分享，浏览器后退能取消筛选，刷新页面也不会丢。参数名与解析只有一份实现（`utils/listFilterParams.ts`），状态只有一个来源（`hooks/useListFilters.ts` 读 `useSearchParams`）—— 不再另存一份在 localStorage 里。
- 排序另有一层回落：用户亲手选过的顺序对所有列表页生效，存在 `store/sortPreference.ts`；地址里的 `sort` 是逐页的显式选择，优先于它。浏览足迹页的天然顺序是「按最近看」，各页没有显式选择时用它。其余筛选不再跨页共享 —— 每页的筛选是这一页的事。
- 工具条的全局搜索框使用独立草稿，列表页自身的 `q` 仍只负责列表筛选；只有 `/photo/search` 与 `/comic/search` 从地址里的 `q` 预填。回车若没有选中某条建议，导航到名称搜索结果页并把关键词写进 `q`；输入时不改当前地址，浏览器返回仍恢复原列表筛选。换排序与视图用 `push`（后退键能退回上一个排序）。
- 查询键集中注册在 `api/queryKeys.ts`：媒体库（`libraryQueryKeys`）、偏好、收藏与最近访问各只有一处定义。键散落在各处各拼各的，「刷新列表」就不知道该失效哪些 —— 手抄一遍字符串，漏一个就有一条旧数据留在界面上。注册表只放键，不放取数函数：取数函数属于各自的 api 模块，测试替换那一层时不必连带替换这里。
- 前端查询键带模式段（`["library", ..., "mode", mode]`），切模式即换键自动重取，旧模式缓存保留。媒体清单与 `nodes/query` 与模式无关，键不带模式。收藏与历史的资源 ID 集合不分类型，由前端按摘要里的 `contentKind` 客户端过滤；`hooks/useFavoritesByMode.ts` 把「当前侧可见的卡片 / 本侧计数 / 真失效的条目」收在一处，收藏页与首页共用它，口径不再分叉。
- 收藏里的智能标签按名解析（`POST /api/tags/query`），接口同时给出两侧的册数：客户端据此区分「这个标签在库里不存在」（失效，可清理）与「它只属于另一侧」（不可见，但不是失效）。把两者混为一谈会导致用户在另一侧点一次「清理失效收藏」就删掉自己的收藏。
- 阅读器整屏脱离 AppShell，侧栏不可见，顶部提供工作台 chip 切模式（切模式即离开阅读器回到外壳）。
- **阅读器的媒体清单与相册页共用同一份查询缓存。** `hooks/useReaderMedia.ts` 走 `useAlbumMedia`（同一个查询键），并把剩下的页依次取完 —— 进阅读器不必重下整本，再次进入时先出图、刷新在后台进行。阅读器页面只留「怎么摆」的部分：取数在 `useReaderMedia`、键盘在 `useReaderKeys`、跨卷导航在 `useAdjacentAlbum`、浮动控件显隐在 `useIdleChrome`。
- 模式也决定视觉基调：`<html data-mode>` 由 `WorkbenchModeProvider` 写入，CSS token 按 `:root[data-theme][data-mode]` 组合覆盖（`--brand*` / `--feature-bg` / `--mode-tint`），画布与文字保持中性灰阶。封面画幅同样按侧取默认值（照片 1:1、漫画 2:3），见 `utils/workbench.ts` 的 `coverRatioForMode`。
- 首页首屏按侧各成一套：漫画是「继续阅读 / 未读」两块面板，照片是「随手看看」的跨相册照片墙，随后依次是「接着看」「那年今日」「最近加入」与一屏主题预览。照片墙的数据源是 `GET /api/library/media-feed?kind=photo&scope=random`（随机几本相册的照片，服务端交错排列），组件在 `components/home/PhotoFeedHero.tsx` 与 `components/wall/PhotoStrip.tsx`（只铺给定张数、不滚动的静态照片条），翻页由 `hooks/useMediaFeed.ts` 负责。照片墙的标题是一个入口，指向随手看看专页 `/photo/random`（`routes/RandomPhotos.tsx`）：那一页的数据源换成 `scope=stream` 的随机长流（`backend/internal/services/library_feed_stream.go`）—— 游标是长流里的照片下标，同一颗种子给出同一条长流，翻页与重进都接得上；走完一圈会绕回开头再来一圈。排布用瀑布流（`components/wall/PhotoMasonry.tsx` 与 `masonryLayout.ts`）：每张按原比例落进当前最矮的一列，与照片墙的 justified（凑行）不同。渲染按视口裁（`hooks/useVisibleWindow.ts`），一次排几千张也不会把 DOM 撑爆。页面上只有「换一批」这一个动作 —— 没有排序、筛选与「最近」。
- **首页是发现页，不是入口页。** 照片侧首页不列全部相册（那是图库）、不列年份索引（那是探索）、不摆完整主题墙（那是探索）；页头只留一句事实（多少本相册、上次更新什么时候）与两个动作（进图库、重新扫描）。漫画侧首页只讲续读与未读，作品与卷的清单在书架 `/comic/library` 里：漫画按作品与卷组织，目录结构对它不是主要路径。
- 照片侧的「接着看」与漫画侧的「继续阅读」对称，数据源不同：漫画读的是阅读进度，照片读的是访问历史。`hooks/useHistory.ts` 的 `useHistoryCards` 把 `GET /api/history` 与 `POST /api/library/nodes/query` 合成按侧收敛的卡片列表，组件 `components/home/ResumeHero.tsx`（首页首屏专区）、侧栏的「继续」区与「最近浏览」页共用它。它额外返回 `resolvedCount`（仍存在于媒体库里的访问记录条数），用来区分「这一侧没有记录」与「访问过的相册全被移出媒体库」——两者的提示语不同，后者才提「相册可能已移动」。
- 措辞与计数单位的唯一真相源是 `utils/workbench.ts` 的词表（`workbenchCopy(mode)`），两侧共用组件从**卡片自身的** `contentKind` 取词，而不是从当前工作台取：一张卡永远知道自己属于照片还是漫画，取不到时按照片兜底。照片说「张 / 本 / 浏览」，漫画说「页 / 卷 / 阅读」。
- 「那年今日」的下标表在发布期建好：把各相册从文件名推断出的拍摄日期按月-日归桶（`library_page.go` 的 `onThisDay`），请求期只按属性与年份过滤。它靠拍摄时间成立，因此只在照片侧有意义 —— 漫画侧不出现这一段。
- 索引维度按侧分：照片按年份（`components/home/YearTimeline.tsx`），漫画按作品（`components/home/SeriesTimeline.tsx`，集合即作品）。两者共用 `components/home/Timeline.tsx` 的视觉骨架。照片侧年份卡的主操作是打开年份照片墙（`routes/YearPhotos.tsx`，`/photo/years/<年份>`）：`GET /api/library/media-feed?kind=photo&scope=year&year=<年份>` 按年份归组取出各相册的照片，每张带 `albumId` / `albumName`，大图预览的标题可点回原相册。

### 查询、导航与网格

`AppShell` 的错误边界重置键把 `/photo/me/:tab` 与 `/comic/me/:tab` 分别折叠到工作台级别，切换「我的」页签时保留已访问面板；设置页和任务中心也按页签共用重置键，其余路径变化仍逐页重挂。

- TanStack Query 管理库、媒体、偏好、收藏与历史；Zustand 管理本机 UI、阅读器和扫描连接会话。主题与 Toast 在应用层统一挂载，阅读器独立于 AppShell 但仍有错误边界与访问门禁。
- 路由在 `App.tsx` 懒加载，**模式进 URL 路径**：`/photo`（照片库首页）、`/photo/library`（图库）、`/photo/explore`（探索）、`/photo/me/:tab`（我的）、`/photo/search`（名称搜索结果）、`/photo/albums/*`、`/photo/tags/*`、`/photo/years/:year`、`/photo/travels`（足迹）、`/photo/people`（人物候选）、`/photo/smart-albums`（智能相册，全库分组的瀑布流墙）、`/photo/random`（随手看看，随机照片墙）；`/comic`（漫画库首页）、`/comic/library`（书架）、`/comic/me/:tab`、`/comic/search`、`/comic/unread`、`/comic/albums/*`、`/comic/tags/*`；漫画阅读器 `/comic/read/:albumId` 使用相册 ID 和 0-based index，视频加 `type=video`；设置页 `/settings` 与模式无关。根路径 `/` 按服务端记住的偏好落到某一侧。标签按单个路径段编码，路径段只解码一次（从原始 pathname 切段，不用 `useParams`），直接打开链接的返回有应用内兜底。旧的 `/photo/recents`、`/photo/favorites`、`/photo/picks`、`/comic/recents`、`/comic/favorites` 重定向到「我的」的对应页签 —— 书签与外链照旧可用。
- **图库（`routes/Library.tsx`）是结构页，不是一张清单。** 左侧 `components/library/FolderTree.tsx` 按需展开真实目录（媒体根 → 集合 → 相册），右侧是当前这一层的内容；当前层、排序、最少张数与视图都住在地址里（`node` 参数加 `hooks/useListFilters.ts` 的查询参数），复制链接能落到同一个文件夹。集合卡在图库里指向它的下一层（`node` 参数），而不是跳去集合页 —— 换目录在图库里比跳出去再跳回来短；集合的规范地址仍是集合页，收藏、属性与复制链接都用规范地址。智能主题（时间、人物、地点、场景的聚合）不进图库：拿自动分组冒充文件夹树，用户就找不到自己的文件。
- 足迹页在 `/photo/travels`，地点详情在 `/photo/travels/place/<六位区划码>`。筛选状态（时间区间 `from`/`to`、时间跨度 `span`、归并粒度 `level`）放查询参数，时间区间是跨层级的一维：换粒度与下钻都带着它，缺省表示全部时间。`span` 取 `1y`/`3y`/`5y`/`10y`/`all`，缺省 `5y`：跨度圈的就是这一段，下面的行程目录与地图随之过滤。旧的 `/photo/locations` 与坐标聚类相册 ID 一并作废，不留兼容跳转。
- 足迹页的组成：`routes/Travels.tsx` 是通栏两栏的骨架（抬头一条带：最左是跨度筛选，随后是规模带，右边是粒度控件，页面名只留在 `sr-only` 的 `h1` 里；正文左栏是行程目录，右栏是地图，`position: sticky` 随页面滚动），`components/travels/TravelMiniMap.tsx` 是右栏那块只读地图（离线行政边界 + 照片位置的点云，320–440 像素见方；`scope` 决定画面是裁到有数据的区域还是整张地图），`components/travels/TravelTrips.tsx` 是行程目录（按年分组，年份倒序，一段一张卡片，宽屏两栏并排，点开才就地展开照片）。段的照片按需取回：`hooks/useChinaLocations.ts` 的 `useChinaTripMedia` 在展开或点开时才发请求。
- **行程不随时间区间重切。** 段是按「粒度 + 两周间隔」切出来的，`/trips/:index/media` 按段的下标寻址 —— 段若随区间重排，下标就再也指不到同一段照片了。因此足迹页的行程列表与行程照片端点**都不带时间区间**，抬头选定的跨度（`span`）与地址里带来的区间（`from`/`to`）只决定哪些段被点亮、地图与地点清单过滤到什么范围；抬头的规模带取的是全量汇总（`useChinaSummaryAll`），说的是这个库的事实。查询键里因此有「全量」与「区间」两套（`useChinaTripsAll` / `useChinaSummaryAll` / `useChinaPlacesAll`），两者不能共用同一个键，否则会互相顶掉。
- **模式有且只有一个真相源：URL 路径前缀。** 服务端 `Prefs.appMode` 只决定根路径落到哪一侧；前端 `appModeStore` 只镜像这个偏好，不持有「当前模式」。`WorkbenchModeProvider`（`components/layout/`）挂在应用最外层，从 `useLocation` 推导模式并经上下文下发，因此整屏脱离外壳的阅读器也在同一套上下文里。切换模式 = 导航到对侧对应页 + 写回偏好，两件事缺一不可。
- 模式切换的语义只有一张表（`utils/path.ts` 的 `counterpartRoute`）：两侧都有的同名页（图库 / 搜索 / 标签 / 「我的」的同名页签）一一对应；相册与阅读器只属于一侧，未读只属于漫画侧，精选只属于照片侧，它们都回落到对侧首页。
- 相册入口按内容属性分派：照片目录的相册 `/photo/albums/<相册 id>` 直接渲染照片墙，漫画目录的相册重定向到阅读器。属性由服务端给出（所属目录的 `kind`），前端不按图片数量推断。
- 照片相册页在原始照片墙与智能分组之间切换。智能分组默认展示精选推荐，并按时间、地点、人物和场景提供详细分类；点开分组后复用同一分页照片墙和大图预览。跨文件夹的汇总专页 `/photo/smart-albums`（`routes/SmartAlbums.tsx`）只展示精选主题；时间、地点、人物、场景详细分组仍由后台生成并缓存，作为推荐计算输入并可在来源相册内浏览。页面固定请求 `dimension=recommended`，不再加载分类目录或计数；旧分类深链会移除 `dimension` 并回到推荐。`/api/smart-albums` 只读取已生成缓存，不为未生成的文件夹触发分析，也不在浏览时重算分组（重算由全库刷新任务负责）；分组仍归属来源相册，卡片链接以 `view=smart`、`dimension` 和 `group` 直达对应分类。照片侧首页的主题预览以不同来源文件夹轮流精选，最多六组；漫画侧首页不摆清单，作品与卷在书架里。分析入口只把当前相册 ID 发给现有分析队列，名称与隐藏操作只写服务端用户状态。推荐维度的空态分「模块没就绪」「分析有失败项」「还没有分析结果」「照片不够」「没形成主题」几种，每种给出对应的下一步；判据取自分析模块安装状态与分析任务记录（推荐维度的 `coverage` 是合并口径，拿不到模块级进度），因此不为判空态额外请求相册级分组摘要。
- **智能相册专页铺成一面等高的方格墙。** 数据源是 `GET /api/smart-albums`（`hooks/useSmartAlbums.ts` 的 `useSmartAlbumDirectory`），默认 `dimension=recommended`；时间、地点、人物、场景为详细分类，`dimension=all` 汇总四类详细分组（不含精选推荐），`dimension=featured` 给首页提供按质量排序并按来源文件夹轮流取样的预览。专页始终请求精选推荐，不发起详细分类目录或计数请求，也不显示分类导航和组数。推荐为默认视图，URL 不保留 `dimension` 参数；旧分类链接会规范化到推荐视图。推荐卡第三行是证据维度芯片（`evidenceDimensions` 映射成时间、地点、人物、场景），质量分只参与后端排序、不上屏；点击后直达对应相册与分组。排布复用照片墙的瀑布流算法（`components/wall/masonryLayout.ts`）：封面**槽位**是正方形（`utils/smartAlbum.ts` 的 `SMART_ALBUM_COVER_SLOT_RATIO`），说明区固定为 74px，因此每张卡等高、行底对齐；照片本身按原比例完整放进槽里、不裁切，空出来的地方用同一张照片放大虚化铺满做底（`components/album/SmartAlbumCover.tsx`），渲染图取哪一档由槽位实际宽度决定，不写死；渲染按视口裁，一次排几千组也不撑 DOM。精选推荐这一页是排序的特例：它排的是跨相册的主题，不按相册分块，整面墙按用户选的 `sort` 排 —— 默认组内最新一张照片的拍摄时间倒序（拍摄时间从元数据记录里取，成员动辄上万条，因此只读这一个字段，不复制整条记录），另有照片张数与推荐分两种排法；排序进了游标的 scope，换排序后旧游标不再适用。往下滑自动接下一批。首页预览批次大小为六，查询键与专页分开；首页只有六张卡，列数取能整除它的因数（`utils/smartAlbum.ts` 的 `smartAlbumPreviewColumns`），末行才不是孤零零一张。
- **汇总按相册排序，来源写在卡上。** 目录接口把同一本相册的分组挨在一起返回，翻的时候认得出「这几组是同一本里的」；相册之间的次序由这本相册「最新的一组」决定：时间维度取那一组封面照片的 EXIF 拍摄时间（组在缓存里就是从新到旧排的，第一组即最新的一组），其余维度取张数最多的那一组，读不到时间信息的相册排在后面。封面图的元数据一次批量取回，不逐本相册去查，因此这一步不额外读文件。前端不再按相册切块 —— 精选推荐收紧后多数相册只剩一条推荐，分块会退化成只挂一张卡的窄带；来源相册写在卡片第二行。
- 常驻导航仅取 activity-summary、随机相册或已加载 dashboard；首页一次取得未读计数、有限预览与在读摘要，不下载全库。完整未读索引按“库 revision + 活动版本”复用，列表按需分页。
- `AlbumGrid` 绑定最近的纵向滚动祖先，网格/列表只挂视口附近条目。
- 照片墙（`components/wall`）按每张图的真实宽高比做自适应排布：宽高比来自服务端媒体分页返回的像素宽高（由 `MediaDimensionService` 读图片头得到并缓存），排布算法是纯函数，容器宽度或密度变化时重算。行高度由算法确定，`Virtuoso` 只负责按行虚拟化；虚拟窗口参数保持在安全范围内，避免尺寸树展开过深触发爆栈。总数占位保留整本相册的滚动长度，行范围换算回媒体序号后由 `useMediaGridPagination` 连续补页，失败保留内容并暂停自动请求，显式重试恢复。容器与窗口的验证要求见设计文档。
- **大图预览跨页连续浏览**（`components/wall/PhotoViewer.tsx`）：预览翻到的位置是「已加载序列」里的下标，序列本身分页到达。翻到已加载末尾时预览自己去取下一页（`hasNextPage` / `onLoadMore`），取到后自动接上下一张，不必回墙上继续；离末尾还有三张时预加载下一页。连按「下一张」时位置记在 ref 里而不是 props 上（props 一次按键只更新一次，连按会被吞掉一半），没加载出来的次数先记着，页到了一次补上。取页失败保留已加载内容并给出手柄（底栏「重试」），再按一次「下一张」也会重试。页数读数报的是服务端总数，不报已加载条数。关掉预览时照片墙按 `scrollToIndex` 回到刚才看的那张 —— 这一条对所有照片墙成立，见下。
- **照片墙的会话状态只有一份实现。** 照片墙散在九处（相册、精选、年份、人物、语义搜索、地点、行程、照片带、随手看看），每处的预览、精选与右键本该是同一件事。`hooks/useWallViewer.ts` 收着大图预览（下标、翻页、关掉后回到刚才那张）、`hooks/usePhotoCompare.ts` 收着并排对比（钉一张、再钉一张成对、互换、关掉）、`hooks/useContextMenu.ts` 收着右键菜单的位置与开关。开着的是哪一张按资源 ID 记，下标由它算出来：分页取到新的一页时列表会变，按下标记的「当前看第几张」会漂到别的照片上。预览的各项属性由 hook 一次算好，各路由只写自己这一页特有的部分（相册级收藏与封面、智能分组的入口）。

- 扫描连接状态与任务状态分开，原生 EventSource 错误不直接等同扫描失败；断线保留进度并阻止重复启动，重连仅 GET 同一任务。“停止跟踪”只释放客户端连接。共享订阅不随路由卸载，迟到/畸形消息不污染新任务。

### 前端布局骨架

页面的版式只有一处真相源，分三层：

- **容器**：`.page-shell` 是唯一的内容容器（`styles/global.css`），宽度由 `--page-max`（2560px）封顶，左右留白由 `--page-gutter`（`clamp(20px, 3vw, 48px)`）给出，并让开安全区（`--safe-left/right`）。所有页面都用它，因此左右留白与内容左缘在翻页时不跳。防御规则 `.page-shell .page-shell` 把嵌套里的内边距清掉 —— 组件内部再套一层容器时不许凭空多出留白。
- **超宽档**：2240px 起（2560 宽的 27 寸）仍是单栏，只是列宽放大、首页页头并成一行；断点在样式表的 `@media (min-width: 2240px)` 与 `hooks/useMediaQuery.ts` 的 `ULTRAWIDE_LAYOUT_QUERY` 两处，改的时候一起改。超宽档不再另做两栏骨架 —— 理由见设计文档的「超宽档版式」。
- **网格**：两套系统各有分工。`.library-grid`（含 `--dense` / `--spacious` / `--comic` 几档）是 CSS 网格，列宽由 `tokens.css` 的 `--library-col` 一族给定，按可用宽度自动分列；`masonryLayout.ts` 是 JS 排的瀑布流，用于照片内容（照片墙、随手看看、智能相册墙），按每张的真实宽高比落进当前最矮的一列。列宽的数值只在 tokens 与 `masonryColumnCount` 的入参里，组件里不写死。

触摸设备另有一套约定：命中区不小于 44×44（`styles/global.css` 的触摸档规则把按钮与链接的本体撑大，视觉尺寸不变），贴边内容让开安全区（`--safe-*`），软键盘弹出时贴底浮层按 `--keyboard-inset` 上移（`hooks/useVisualViewport.ts`）。设计意图与理由见设计文档。

### 活动、收藏与历史

- 精选（`state/picks.json`）与收藏是两份数据、两种语义：收藏标记「这一本值得留着」，
  精选标记「这一张值得留着」。两者各写各的文件，互不覆盖也不会互相清理 ——
  「清理失效收藏」不会动精选。精选只属于照片侧：照片墙与精选页都是照片侧的界面，
  漫画那边有阅读进度与已读状态。精选条目是媒体文件 ID（`f_`），上限 5000 条。
  内存里同时留有序列表与集合：列表给展示顺序（最近加入在前），集合给 O(1) 的
  「这张在不在精选里」——照片墙每一格都要问一次。写入是整份文件原子替换，
  与收藏同一套做法；5000 条的量级下单次落盘在毫秒级，不需要另设增量日志。
- 精选与目录数据分属两处：目录快照里不存精选，请求期按当前精选集合给媒体项打
  `picked` 标记。精选页要跨相册列出这些照片，因此目录侧另建一张「文件 ID → 所属相册
  与序号」的反查表（存下标不存副本，避免为大库再留一份媒体摘要）；同一份文件同时
  出现在真实相册与「本目录媒体」虚拟相册时优先用真实相册，判定不依赖 map 遍历顺序。
- 精选页的分页游标作用域里带精选自身的版本号：精选一变，旧游标立即失效，
  新加入的照片不会把已经翻过的页顶走一格。
- 漫画按 `albumId + image` 保存页码；视频按 `albumId + video + itemId` 保存毫秒位置。图片最后一页、视频 98% 派生完成；无图片活动表示未读，纯视频相册改用视频活动。照片浏览不留进度记录，因此没有 `photo` 活动类型。
- 未读判定只针对漫画相册（看 `image` 活动）；照片目录下的相册不记录进度，也就不存在未读。
- 阅读进度恢复成功前禁止写入，只有明确的 `activity_not_found` 可当新记录；其他失败持续提示并可重试，避免自动播放/初始页覆盖旧位置。保存失败重试使用当前有效位置，切资源忽略旧失败，卸载 keepalive 仅尽力写入。
- `useImageProgressSync` 收拢图片进度的 600ms 去抖、保存反馈与确认后的缓存刷新。浏览分页的卡片进度只补充已加载漫画的活动，保留在读与已完成状态。`activityApi` 持有会话级图片写入队列：串行发送，尚未发送的同相册进度合并为最新值；相同在途请求可共享确认。显式已读、重置、批量操作和活动备份恢复形成边界，不跨边界合并。失败拒绝相关等待者后继续后续任务，不自动重放写入。
- 图片卸载补写经过同一队列，已发送的小请求带 `keepalive`；浏览器关闭后尚未发送的任务只能尽力补写，收到成功响应才代表已落盘。队列只协调当前浏览器会话，不提供多标签页的全局顺序。
- `useVideoActivity` 收拢视频恢复、节流保存与卸载补写，回调通过 ref 转发以避免查询重启；视频播放状态保持独立。活动写入由应用级 `useLibraryActivitySync` 统一失效首页、计数与未读缓存。
- 活动状态以 JSON 持久化。图片进度已使用去抖与会话内串行合并降低写入频率，但真实大库高频翻页下的写盘成本尚未单独量化；存储改造前需先建立可复现基线。
- 收藏/历史/偏好写入成功后先将服务端确认结果写共享查询缓存，再后台刷新，后续 GET 失败不能复活已删除记录或回退新设置。切换收藏读取当前缓存，首次查询未确认不盲写；清理失效项只过滤已知缓存，不凭移除清单构造空列表。
- 首页、集合与标签相册使用 `useLibraryList` 无限分页，服务端 `library_query.go` 统一筛选与排序。每个不可变库快照拥有最多 16 个查询结果的 LRU，翻页复用结果；游标同时绑定查询与历史排序快照。年份/作品索引和统计独立于已加载页数。请求取消、后续页重试和游标失效后的整链重取由 hook 处理。阅读器上下文携带查询及后续游标，在已加载边界补页，卸载/换卷取消请求；失败提示返回列表刷新，不混用旧顺序。
- 列表排序共用一套口径：「按拍摄时间」（照片侧）/「按加入时间」（漫画侧）用业务日期（拍摄时间 > 文件夹名日期 > 修改时间），与后端 `albumMoreRecent` 相同；缺业务日期时退回修改时间。图库、集合、标签由服务端执行；收藏与最近等有界列表继续使用 `utils/cardSorting.ts`。列表默认不重复摆年份归组的那些集合（`library_query.go` 的 `excludeYearTargets`），搜索或按年份筛选时仍给出全部命中。
- 最近与收藏分别处理查询失败、资源失效和筛选无结果，保留已加载卡片。“最近看”只在需要排序时读历史，按 `openedAt` 降序，同时间或未访问按名称；历史只有这一份缓存：收藏与最近访问各有独立接口，偏好响应不再带这两个字段，客户端也不另存副本。
- 照片侧的访问记录记到相册：打开相册页记一条，看照片（大图预览）也记它出自的那本相册 —— 用户翻的是照片，落点却是相册。跨相册的照片墙里相册随照片变，`useVisitRecorder` 按相册冷却 30 秒，避免连翻几十张时写盘次数跟着照片数走；打开相册页不走冷却，刚打开的这本总要排在最前。记录只依赖相册身份，不随媒体分页重复写入。
- 访问记录使用真实相册名称和图片总数，只依赖相册身份，不随媒体分页重复记录；视频数量不替代图片总数。可点击星标与链接分离，星标使用共享 mutation，不为每张卡订阅完整收藏列表。

### 服务端配置表单

`useServerConfigSave` 在同一 QueryClient 内通过共享 mutation scope 串行写入，覆盖卸载重进；LAN 凭据变更后的会话建立也属于该串行流程。保存开始/确认取消旧 GET，读取传递 AbortSignal 并禁用 HTTP 缓存，防止迟到读取回退新值。

- 显示优先级为草稿 → 最新保存中值 → 失败输入 → 确认值，状态与当前可见值对应。失败输入仅在会话内缓存，保留 false/0/空数组，不持久化路径或令牌，凭据不进入失败缓存。
- 输入法组合期间，媒体根整组或当前文本/数字字段暂停自动保存；确认后重新计时并核对草稿版本。失焦确认组合输入，删除字段/卸载清理未提交计时，已发出的请求按序完成。Enter/Esc 语义见快捷键文档。
- 重试仅提交未被新草稿或排队写入覆盖的失败值；显式重新读取在无排队写入时执行，暂禁表单，失败/取消/卸载保留输入，忽略迟到结果。
- 根目录写入遇到网络/超时/5xx 时标记结果待确认，不能推断服务端没写入。重试或读取确认后清客户端旧库并提示扫描；结果未确认、新根草稿或保存中禁用扫描。Esc 只撤销本地输入。
- 目录选择只在本机管理接口浏览，后端返回路径与平台根，前端不探测 OS/拼路径；弹窗持有临时路径、取消旧请求并忽略迟到结果，确认才进入配置保存流程。后端每批读取 256 项、使用固定大小堆生成最多 200 项有序页，不缓存完整目录。

属性、菜单、帮助、复制与系统打开复用现有组件/hooks。属性按节点/图片类型请求，聚合标签不冒充目录；复制优先剪贴板 API、失败用所属 dialog 内临时选区并恢复焦点；系统打开权限用 `useFsCapabilities` 共享查询，未知时关闭，设置确认后取消旧查询并发布权限。键盘细节只在快捷键文档、视觉细节只在设计文档维护。

### 相似照片特征提取与分组对照

2026-11-18，Windows 16 核，本机照片库 13,478 张（含 101 兆像素、71 MB 的单张），跑完整量相似照片特征分析。

吞吐：13474 张成功、4 张无法解码（文件本身损坏），平均约 4.3 张/秒，整轮约 52 分钟。成本几乎全在 JPEG 解码上：抽样的最大文件解码一次 1.86 秒、折算到长边 1024 再 233 毫秒，而中位大小（约 4.5 MB）的照片解码约 220 毫秒。折算副本保持原比例、并发按核数给满之后，单张的额外开销（读文件头、折算、哈希）不到解码的十分之一。

内存：解码预算 768 MB，按像素数分配，大照片自动串行。服务进程在整轮分析中的工作集峰值约 3.5 GB（含 Go 的堆保留），单张百兆像素照片解码后约 400 MB。

分组：重算 13,474 张照片的全部分组耗时 1.7 秒，候选召回未触顶。结果为 236 组完全重复、742 组近似重复、1,670 组连拍同场景，合计 4,428 张多余照片。候选召回采用分带索引加逐对复核，去重靠世代标记而非全局集合，内存只与照片数成正比。

误报与漏报：逐组展开人工核对前若干组，近似重复组确实是同一画面的重压缩与裁切版本（感知哈希距离 0～8），连拍组确实是同一场景的不同帧（语义相似度 93%～100%，主体位置不同），未见误报。漏报方面没有构造穷举基准：分带索引对汉明距离不超过 7 的哈希有召回保证（鸽笼原理），裁切档位覆盖 1.0/0.8/0.6 三个中心区域，更大幅度的裁切与「相似但不同」的照片之间的边界没有系统评测。

派生体积：每张照片的特征约 200 字节（内容指纹、四个 64 位哈希、尺寸与四个质量分项），13,478 张约 2.6 MB，写在 `derived/metadata/similarity/batches/`；分组结果本身不到 1 MB。

### AI 图像嵌入预处理对照

2026-11-15，Windows / NVIDIA RTX 3060 12GB，同一固定合成集 180 张、9 条查询，使用当前 Chinese-CLIP 权重分别运行串行与 4 线程图像解码/预处理。一个最多 32 张的图像嵌入请求 p50 从 161.37 ms 降到 134.53 ms（约快 16.6%），6 次请求的 p95 从 3,257.20 ms 降到 2,566.49 ms；GPU 峰值分配均为 447,369,728 B。Top-10 精确率均为 1.0、召回率均为 0.5，OCR 固定集仍为 8/8 精确。p95 包含第一次加载与预热，合成集不代表个人照片库；性能对照用来确认没有回退，不作为实际媒体吞吐承诺。

同日保持 4 线程预处理和同一 180 张合成集，对比 GPU 子批次 8、16、32，每个配置测两轮。每轮 6 个图像请求的 p50 再取中位数，分别为 132.37、125.66、122.84 ms；32 相比 8 快约 7.2%。Top-10 精确率/召回率三组均为 1.0/0.5。CUDA 峰值分配约为 447、493、585 MiB；批次上限提高以显存为代价，CUDA OOM 会逐半减小批次。样本仅用于比较同机性能，不代表个人照片库吞吐。

### OCR 分类与识别批次对照

同日使用 RTX 3060 12GB、8 张合成页（每页 32 行，共 256 行），先预热 2 次，再测 7 轮完整批次。修复 DLL 搜索路径前，GPU 请求静默使用 CPU，中位耗时 23,716 ms、吞吐 10.79 行/秒；修复后同一默认批次下实际使用 CUDA，中位耗时 6,208 ms、吞吐 41.23 行/秒，约快 3.8 倍。RapidOCR 默认分类/识别批次均为 6 时，7 轮最大值 6,402 ms；GPU 分类批次改为 16、识别批次保持 6 后，中位耗时降至 5,111 ms（再快约 17.7%），最大值 5,236 ms，吞吐 50.09 行/秒，8/8 页面完全匹配、字符错误率为 0，三个已加载 session 都使用 CUDA。分类批次32中位耗时 5,155 ms，没有继续提速；识别批次16会使 PP-OCRv6 session 回退到 CPU。`nvidia-smi` 系统级已用显存增量分别约为 1,499、1,534 和 1,543 MiB（批次6、16、32），不按进程隔离，仅用于同机粗略比较。CPU-only 单页 32 行的 7 次测量中，分类批次6/16中位数分别为 3,026/2,986 ms，差距处于轮间波动内。另测 4 张合成页、每页 32 行：默认 ONNX Runtime 线程设置下串行中位 12,066 ms；设为 1 个线程后串行 24,689 ms、4 路并发 13,564 ms；设为 4 个线程并发时 12,416 ms。各配置均为 4/4 页面完全匹配，未超过默认串行吞吐，因此 CPU OCR 保持默认线程数与串行调度。合成页不代表个人媒体库，结果不作为实际吞吐承诺。

### 活动重复写入对照

2026-11-09 在 Windows / Intel i7-10700K 上，临时生成 1,000 / 10,000 / 100,000 条活动，每组提交 20 次相同进度；初始化与首次落盘不计时。优化前使用 `3219227` 的活动存储源码，优化后使用当前实现，基准代码与参数相同。p95 使用 Go benchmark 的高精度计时，内存为分配字节/次，不是进程峰值。

2026-11-16 在同一台 Windows / Intel i7-10700K 上，活动写入改为单写者串行；数据复制、排序、JSON 编码和原子落盘期间，读请求继续读取旧的不可变快照，落盘成功后再发布新快照。使用 1,000 条活动、20 次交替进度更新的并发读基准，读取 p95 从 28.37ms 降到 0.5μs。基准通过 `go test ./internal/store -run '^$' -bench '^BenchmarkActivityReadWhileRepeatedWrites$' -benchtime=20x -benchmem` 运行；旧实现与新实现均使用修正后的基准代码。该结果只衡量读锁等待，不代表写入不再是 O(N)。单轮写入基准的吞吐、p95 与分配分别为 20.56 次/秒、104.57ms、1,926,363 B/op 和 71.17 次/秒、18.79ms、1,885,404 B/op；写入数据受本机原子文件替换与同步影响，单轮结果不作为写吞吐承诺。
